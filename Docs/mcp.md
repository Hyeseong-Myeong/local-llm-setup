# 📄 제안서: Open WebUI와 옵시디언(Obsidian) 지식 기반 연동 방안

**작성 목적:** 로컬 환경에서 구동 중인 Open WebUI에 팀의 옵시디언 지식 기반(Knowledge Base)을 연동하기 위한 두 가지 방안을 비교하고, 안정성과 시스템 일관성을 위한 최적의 아키텍처를 제안합니다.

---

## 1. 배경 및 현재 시스템 컨텍스트 (Background Context)

현재 우리 팀은 완벽하게 프라이빗한 로컬 AI 환경을 구축하여 사용 중입니다.
* **코어 AI:** Open WebUI + Ollama (`qwen3.5:9b`, `EXAONE 3.0` 등 소형~중형 로컬 모델 위주 사용)
* **지식 관리 자동화 (`wiki_agent.py`):** 디스코드나 스크래핑을 통해 수집된 정보를 마크다운 형태의 옵시디언 문서로 컴파일하고 있습니다.
* **독자적 벡터 DB 구축:** 자동화 에이전트가 문서를 저장할 때 자체적으로 **ChromaDB(포트 8000)**에 임베딩하여 RAG(검색 증강 생성)용 데이터를 유지 및 관리하고 있습니다.

이제 이 옵시디언에 쌓인 지식을 채팅 인터페이스(Open WebUI)에서 직접 검색하고 대답하게 만들고자 합니다. 이를 구현하기 위한 두 가지 방안을 분석했습니다.

---

## 2. 방안 비교 분석

### 방안 A: 단순 파일 연결 (Open WebUI 내장 RAG 활용)
Open WebUI의 [문서(Documents)] 기능이나 [디렉토리 스캔] 기능을 통해 옵시디언 폴더를 통째로 Open WebUI에 업로드/연동하는 방식입니다.

* **장점 (Pros):**
  * 추가적인 코드 개발이 필요 없으며, UI 상에서 즉시 설정이 가능합니다.
* **단점 및 리스크 (Cons & Risks):**
  1. **[치명적 위험] RAG 템플릿 충돌 및 환각 발생:** 
     과거 트러블슈팅(참조: `troubleshooting.md`)에서 겪었듯, Open WebUI의 내장 RAG를 활성화하면 사용자 몰래 모델의 뒷단에 *"반드시 [id=1] 형태로 출처를 표기해라"* 라는 강제 시스템 프롬프트가 주입됩니다. 로컬에서 사용하는 10B 이하의 소형 모델들은 이 지시와 사용자의 지시 사이에서 인지 부조화를 일으켜 텍스트 포맷이 붕괴되거나 가짜 출처를 생성하는 치명적인 버그가 있었습니다.
  2. **지식 DB의 파편화 (중복 리소스):**
     이미 `wiki_agent.py`가 고품질의 임베딩을 거쳐 자체 ChromaDB를 관리하고 있는데, Open WebUI가 또 자신만의 내부 벡터 DB를 구축하게 되어 데이터와 서버 리소스(디스크/메모리)가 중복 낭비됩니다.
  3. **옵시디언 마크다운 구조 무시:**
     단순 텍스트 청킹(Chunking)을 수행하므로, 옵시디언의 핵심인 메타데이터(YAML Frontmatter)나 양방향 역링크(`[[ ]]`)의 문맥을 잃어버리게 됩니다.

### 방안 B: 사용자 정의 툴(Open WebUI Tool) 또는 MCP 직접 구현 🌟 (추천)
Open WebUI가 내장 기능으로 제공하는 **파이썬 사용자 정의 도구(Tools)** 기능을 활용하거나, 표준 **MCP(Model Context Protocol)** 서버를 구축하여 기존 지식 베이스를 연동하는 방식입니다.

* **장점 (Pros):**
  1. **기존 인프라 완벽 재활용:** `wiki_agent.py`가 실시간으로 관리하는 기존 ChromaDB(8000포트)를 그대로 쿼리하거나, 옵시디언 로컬 디렉토리를 직접 읽어올 수 있어 DB 중복을 막을 수 있습니다.
  2. **RAG 템플릿 부작용 완벽 회피:** 내장 RAG 파이프라인을 타지 않고 일반 '웹 검색 툴'처럼 모델에게 텍스트 컨텍스트만 순수하게 전달하므로, 강제 출처 표기 프롬프트가 주입되지 않아 포맷 붕괴나 환각을 원천 차단할 수 있습니다.
  3. **옵시디언 맞춤형 고급 검색:** 
     * "YAML 태그에 `#tech`가 있는 문서만 찾아줘"
     * "특정 파일명(`[[AI_어쩌고]]`)의 원본을 그대로 읽어와 줘" 
     같은 맞춤형 파이썬 로직을 구현하여 옵시디언에 최적화된 검색이 가능해집니다.
* **단점 (Cons):**
  * 파이썬 스크립트 작성 등 약간의 초기 개발 공수가 발생합니다. (단, 단일 Python 파일 수준이므로 유지보수 부담은 극히 적습니다.)

## 3. 결론 및 향후 진행(Next Step) 제안

로컬 LLM의 구조적 한계(RAG 프롬프트 충돌에 취약함)와 현재 이미 잘 구축된 `wiki_agent.py`의 ChromaDB 인프라를 고려할 때, **방안 A(단순 파일 연결)는 득보다 실이 많으며 시스템의 불안정성을 초래할 가능성이 매우 높습니다.**

따라서 팀 내 지식 연동은 **방안 B (직접 Tool/MCP 구현)** 로 진행하는 것을 강력히 제안합니다. 

**[실행 계획 (Action Items)]**
거창한 외부 MCP 서버를 별도로 구동하기보다는, Open WebUI의 **Tools 밸브(Valves)** 기능을 사용하여 단일 파이썬 스크립트 기반의 도구를 개발하는 것이 가장 효율적입니다.
1. **ChromaDB 연동 툴:** 8000번 포트에 띄워진 ChromaDB를 쿼리하여 유사도가 높은 위키 텍스트 조각을 반환하는 Tool 스크립트 작성
2. **Obsidian File Reader 툴 (선택):** 파일명을 전달받으면 해당 파일의 전문을 읽어서 LLM에게 넘겨주는 보조 툴 작성
3. 개발된 스크립트를 Open WebUI의 Tools 탭에 복사하여 붙여넣고 전역 활성화 수행
