## 1. 배경 — 왜 이 실험이 필요한가

섹션 17에서 확인된 것:

* 게이트웨이(Bifrost)가 출력 상한(`max_tokens`)을 Ollama 로 전달하지 못한다. **버전과 무관한 결함**이며 클라이언트 측 우회법이 없다.
* thinking 모델은 상한이 없으면 수천 토큰까지 자유 생성한다.
* 상류 이슈는 **클라이언트가 연결을 끊어도 상류 생성이 취소되지 않는다**는 점도 지적한다. 즉 한 번 시작된 폭주는 클라이언트 쪽에서 멈출 수 없다.

지금 유효한 완화책은 **모델 자체에 상한을 내장하는 것**(Ollama Modelfile `PARAMETER`)뿐이다. 그런데 그 값을 **감으로 정하면 양쪽으로 실패한다**.

| 값이 너무 낮으면 | 값이 너무 높으면 |
|---|---|
| 위키 문서가 조용히 잘린다 | 폭주를 못 막는다 |
| thinking 모델은 사고에만 상한을 다 쓰고 **본문이 빈 채로** 끝난다 (섹션 11 증상 18과 같은 양상) | GPU 가 묶여 다른 소비처가 대기한다 |

**따라서 "하드웨어가 어디까지 버티는가"를 먼저 실측해야 상한값을 근거 있게 정할 수 있다.** 이 문서는 그 측정의 설계다.

## 3. 무엇을 재는가

### 3-1. 핵심 지표 — GPU/CPU 분할

**이것이 유일한 직접 신호다.** VRAM 이 부족하면 Ollama 는 **실패하지 않고** 일부 레이어를 CPU 로 내린다. 에러가 없으므로 **조용한 성능 붕괴**로 나타난다 — 섹션 14·17에서 반복해서 확인한 "조용한 실패" 계열과 같은 성질이다.

```
ollama ps
NAME    ID    SIZE    PROCESSOR    CONTEXT    UNTIL
```

* `PROCESSOR` 가 `100% GPU` 이면 전부 VRAM 에 올라간 것이다.
* `48%/52% CPU/GPU` 같은 형태가 나오면 **그 지점이 상한을 넘은 것이다.**
* `CONTEXT` 컬럼으로 실제 적용된 컨텍스트 길이를 확인한다 — 요청한 값과 다를 수 있으므로 **가정하지 않고 읽는다.**

### 3-2. 보조 지표 — 처리량과 지연

Ollama `/api/chat` 응답의 원시 필드를 쓴다.

| 필드 | 의미 | 파생 지표 |
|---|---|---|
| `load_duration` | 모델 적재 시간 | 상한 초과 시 급증 |
| `prompt_eval_count` / `prompt_eval_duration` | 프롬프트 처리 | 프롬프트 처리 속도 |
| `eval_count` / `eval_duration` | 생성 | **토큰/초 = `eval_count / (eval_duration / 1e9)`** |
| `done_reason` | 종료 사유 | `length` 면 상한 적용, `stop` 이면 자연 종료 |

**토큰/초가 급락하는 지점과 `PROCESSOR` 가 깨지는 지점이 일치하는지** 확인하는 것이 이 실험의 교차 검증이다.

### 3-3. 재지 않는 것 — 명시해 둔다

* **VRAM 사용량 자체는 재지 않는다.** Windows + ROCm 환경에서 신뢰할 수 있는 조회 수단이 확인되지 않았다. `PROCESSOR` 분할이 대리 지표다.
* 게이트웨이 경유 성능은 재지 않는다. **Ollama 직접 호출만 한다** — 게이트웨이는 `num_ctx`·`num_predict`를 전달하지 못하므로 이 실험을 수행할 수 없다.

## 4. 실험 설계

### 실험 A — 정적 컨텍스트 상한 탐색 (주 실험)

**목적:** 모델별로 **100% GPU 적재를 유지하는 최대 `num_ctx`** 를 찾는다.

**전제:** Ollama 는 `num_ctx` 만큼의 KV 캐시를 **적재 시점에 미리 확보한다.** 따라서 상한은 생성 중이 아니라 **적재 시점에 결정된다.** 이것이 이 실험을 정적으로 설계할 수 있는 근거다.

**절차 (모델 1개당):**

1. 해당 모델을 언로드한다 (`keep_alive: 0`).
2. 후보 `num_ctx` 값으로 **아주 짧은 요청**(`num_predict: 1`)을 보내 적재만 시킨다.
3. `ollama ps` 로 `PROCESSOR` · `SIZE` · `CONTEXT` 를 읽는다.
4. 결과를 기록하고 다음 후보로 넘어간다.

**후보 값:** `2048 → 4096 → 8192 → 16384 → 32768 → 65536`
모델 최대 컨텍스트를 넘는 후보는 건너뛴다.

**판정:**

| `PROCESSOR` | 판정 |
|---|---|
| `100% GPU` | 통과 — 다음 후보로 |
| CPU 가 섞임 | **상한 초과.** 직전 통과값이 그 모델의 실용 상한 |
| 적재 실패 / 타임아웃 | 상한 초과로 간주하고 중단 |

**중단 조건:** 첫 실패 이후 **더 큰 값을 시도하지 않는다.** 단조 증가 관계를 전제하므로 계속 시도할 이유가 없고, 시간과 VRAM 만 낭비한다.

### 실험 B — 생성 길이에 따른 처리량 곡선

**목적:** KV 캐시가 차면서 생성 속도가 떨어지는지, 떨어진다면 어느 정도인지 본다.

**절차:** 실험 A 에서 찾은 상한 `num_ctx` 로 고정하고, `num_predict` 를 `128 → 512 → 1024 → 2048` 로 늘리며 토큰/초를 기록한다.

**보는 것:** 토큰/초가 생성량에 따라 어떻게 변하는가. **평탄하면** 상한값을 지연시간 기준으로만 정하면 되고, **뚜렷이 떨어지면** 긴 생성 자체가 비용이므로 상한을 더 보수적으로 잡아야 한다.

### 실험 C — thinking 모델의 자연 생성량 분포

**목적:** "폭주"의 실제 규모를 숫자로 만든다. 상한값을 정하려면 **막으려는 대상의 크기**를 알아야 한다.

**절차:** thinking 모델(`qwen3.5:9b`, `deepseek-r1:14b`)에 **상한 없이** 대표 프롬프트를 N회 반복하고 `eval_count` 분포를 기록한다.

**보는 것:** 중앙값과 최댓값. 상한은 **정상 응답의 최댓값보다 위, 폭주의 중앙값보다 아래**에 두어야 의미가 있다.

## 6. 실험 후 결정할 것

> **이 절은 실행 전에 작성한 것이며 그대로 둔다.** 실제 결과와 결론은 **7장 「결론」** 참조. 두 곳을 대조하면 설계 시점의 예상이 어디서 맞고 어디서 빗나갔는지 보인다.

이 실험은 그 자체가 목적이 아니라 **아래 결정을 위한 입력**이다.

1. **모델별 권장 `num_ctx`** — 100% GPU 를 유지하는 값.
2. **모델별 권장 `num_predict`** — 실험 B·C 를 종합해 정한다.
3. **Modelfile 파생 모델을 만들 것인가.** 만든다면 어느 소비처에 적용할 것인가.
   * 벤치마크처럼 짧은 상한이 필요한 곳에만 적용하고, `wiki_agent` 처럼 긴 출력이 정상인 곳은 원본 모델을 유지한다.
   * **한 모델에 상한을 박아 전 소비처에 적용하면 위키 문서가 조용히 잘린다.**
4. **8GB 를 넘는 모델(`deepseek-r1:14b` · `phi4` · `gemma4:e4b`)을 계속 쓸 것인가.** 실험 A 가 예상대로 나오면 이 셋은 항상 CPU 분할 상태이며, 라우팅 맵에서 우선순위를 낮추는 근거가 된다.

## 7. 측정 결과 (2026-08-22 실측)

측정 조건 — `wiki_agent` 와 `fastapi_wiki_server` 를 정지한 상태에서 실행했다(`discord_bot` 은 GPU 를 쓰지 않아 유지). 원시 결과는 `tmp/ctx_a.json` · `tmp/ctx_a2.json` · `tmp/ctx_b.json` · `tmp/ctx_c.json`.

### 실험 A — 컨텍스트 상한

| 모델 | num_ctx | GPU | 적재 크기 | 판정 |
|---|---|---|---|---|
| `qwen2.5-coder:7b` | 2,048 | 100% | 4.62GB | 통과 |
| | 4,096 | 100% | 4.74GB | 통과 |
| | 8,192 | 100% | 5.12GB | 통과 |
| | 16,384 | 100% | 5.46GB | 통과 |
| | **32,768** | **100%** | **6.41GB** | **통과 — 모델 최대치까지 도달** |
| `qwen3.5:9b` | 2,048 | 100% | 5.58GB | 통과 |
| | 4,096 | 100% | 5.65GB | 통과 |
| | 8,192 | 100% | 5.79GB | 통과 |
| | 16,384 | 100% | 6.06GB | 통과 |
| | **32,768** | **100%** | **6.62GB** | **✅ 상한 확정** |
| | 65,536 | **78.1%** | 8.67GB (VRAM 6.77GB) | 🔴 CPU 분할 |
| `deepseek-r1:14b` | 2,048 | **69.6%** | 9.56GB (VRAM 6.66GB) | 🔴 최소 후보에서도 실패 |

**읽어낸 것:**

* **VRAM 실효 예산은 약 6.7~6.8GB 다.** 8GB 카드지만 두 번의 분할 지점이 각각 6.66GB · 6.77GB 에서 나타났다. 나머지는 디스플레이·드라이버 몫으로 보인다.
* **`qwen3.5:9b` 의 상한은 `num_ctx=32,768` 로 확정됐다.** 다음 후보(65,536)에서 CPU 분할이 관측됐으므로 캡이 아니라 실제 한계다.
* `qwen2.5-coder:7b` 는 **모델 자신의 최대치(32,768)까지 100% GPU** 다. 하드웨어가 아니라 모델이 상한이다.
* **`deepseek-r1:14b` 는 예상대로 어떤 컨텍스트에서도 100% GPU 가 불가능하다.** 최소 후보인 2,048 에서도 30%가 CPU 로 내려간다. 3절의 예상이 확인됐다.

### 실험 B — 처리량 곡선 (`qwen3.5:9b`, `num_ctx=32,768`)

| num_predict | 토큰/초 | eval_count | done_reason |
|---|---|---|---|
| 128 | 24.5 | 128 | `length` |
| 512 | 24.3 | 512 | `length` |
| 1,024 | 24.3 | 1,024 | `length` |
| 2,048 | 24.2 | 2,048 | `length` |

**처리량이 평탄하다.** 생성량이 16배 늘어도 24.5 → 24.2 tok/s 로 사실상 변화가 없다.

> **이것이 상한값 결정에 주는 함의:** **폭주의 비용은 성능 절벽이 아니라 순수한 시간이다.** 컨텍스트 안에서는 KV 캐시가 차도 속도가 떨어지지 않으므로, 상한은 "어디서 느려지는가"가 아니라 **"얼마나 기다릴 수 있는가"** 로 정해야 한다.
>
> 모든 행이 `done=length` 인 것도 확인 사항이다 — Ollama 직접 호출에서는 상한이 정확히 적용된다(섹션 17).

### 실험 C — 자연 생성량 분포 (`qwen3.5:9b`, 상한 없음, 3회)

| 회차 | eval_count | done_reason | 토큰/초 |
|---|---|---|---|
| 1 | 2,221 | `stop` | 22.4 |
| 2 | 1,810 | `stop` | 22.9 |
| 3 | 2,123 | `stop` | 22.7 |

**중앙값 2,123 · 최대 2,221 · 최소 1,810.** 22.7 tok/s 기준 **호출당 약 93초**다.

* 섹션 17에 기록된 벤치마크 관측(2,121토큰 / 104.99초)과 일치한다. **재현성이 있다.**
* 이 프롬프트는 *"관측성이 왜 중요한지 설명해줘"* 라는 **평범한 한 문장 질문**이다. 특별히 긴 답을 요구하지 않았는데도 2,000토큰을 넘긴다.

### 실험 D — 다중 턴에서 대화가 끊기는 현상 (실사용 증상 추적)

> 실사용 보고: **"대화를 2~3턴 주고받다보면 끊기는 일이 잦다."**
> 실험 A~C 는 이 증상을 설명하지 못한다. A 는 *적재 시점* 상한만 쟀기 때문이다. 추가 측정했다.

#### D-1. 실효 컨텍스트는 4,096 이고, 게이트웨이로는 올릴 수 없다

| 경로 | 적용된 `context_length` |
|---|---|
| Ollama 직접 · 옵션 없음 | **4,096** (Ollama 기본값) |
| Bifrost 경유 · 옵션 없음 | **4,096** |
| Bifrost 경유 · `options.num_ctx=16384` | **4,096 — 무시됨** |

**`OLLAMA_CONTEXT_LENGTH` 는 설정돼 있지 않다.** 그리고 **Bifrost 는 `num_ctx` 도 버린다** — 섹션 17의 `max_tokens` 와 같은 계열이다.

> 실험 A 에서 하드웨어가 **32,768 까지 100% GPU** 로 버틴다고 측정했는데, **운영 경로는 그 1/8 인 4,096 을 쓰고 있다.** 하드웨어 여유를 전혀 못 쓰는 상태다.

#### D-2. 빈 응답 — 사고가 컨텍스트를 다 써 버린다

동일 질문(*"고양이 이름이 뭐라고 했죠? 이름만 짧게"*)에 대한 Ollama 직접 응답:

| 필드 | 값 |
|---|---|
| `content` | **길이 0 — 비어 있음** |
| `thinking` | **17,470자** |
| `eval_count` | **4,058** |
| `done_reason` | **`length`** |

**모델이 4,058 토큰을 사고에만 쓰고 4,096 컨텍스트를 소진해 본문을 한 글자도 내지 못했다.** 사용자에게는 빈 응답, 즉 *"끊김"* 으로 보인다.

5턴 대화 실측에서도 같은 일이 났다 — 마지막 턴이 `completion_tokens=684`, `finish_reason=stop` 인데 **`content` 가 빈 문자열**이었다. 즉 빈 응답에는 두 경로가 있다.

| 경로 | 조건 |
|---|---|
| (a) `done_reason=length` | 사고가 남은 컨텍스트를 초과 |
| (b) `done_reason=stop` | 한계 전이라도 사고만 하고 본문 없이 턴을 끝냄 |

#### D-3. 사고 길이 편차가 크다 — 그래서 간헐적이다

같은 질문을 반복했을 때 `eval_count`:

| 표본 | 값 |
|---|---|
| 관측된 범위 | **428 · 438 · 448 · 515 · 575 · 931 · 1,595 · 1,825 · 2,631 · 4,058** |

**한 자릿수 배 이상 흔들린다.** 재현 시도 3회에서는 빈 응답이 0/3 이었다 — **실패는 확률적이며, 짧은 시행으로는 재현되지 않을 수 있다.**

#### D-4. 왜 하필 2~3턴 뒤인가 (측정값에 근거한 추론)

다중 턴 실측에서 `prompt_tokens` 누적:

| 턴 | prompt_tokens | 증가 | completion_tokens |
|---|---|---|---|
| 1 | 40 | — | 903 |
| 2 | 300 | +260 | 818 |
| 3 | 403 | +103 | 953 |
| 4 | 960 | +557 | 906 |
| 5 | 1,458 | +498 | 684 (**본문 없음**) |

* **사고 토큰은 히스토리에 되먹여지지 않는다.** `completion_tokens` 가 900 인데 다음 턴 prompt 는 260 만 늘었다. 그래서 히스토리 누적만으로 4,096 을 넘기려면 턴이 훨씬 많이 필요하다.
* **지배적인 요인은 히스토리가 아니라 턴마다의 사고 폭증이다.** 남은 예산 = `4,096 − prompt_tokens` 이므로 턴이 쌓일수록 예산이 줄고, 사고 길이 분포는 그대로다 → **실패 확률이 턴마다 올라간다.**
  * 1턴 예산 약 4,056 → 4,058 급 폭증이라야 실패
  * 5턴 예산 약 2,638 → **1,825 급 폭증만으로도 위험 구간**
* 이것이 *"2~3턴 뒤부터 잦아진다"* 와 일치한다. **다만 이 인과는 측정값에 기반한 추론이며, 턴별 실패율을 직접 세지는 않았다.**

#### D-5. 두 번째 "끊김" 경로 — 대기 시간

같은 질문에 **118초**가 걸린 시행이 있었다(사고 2,631토큰). 다중 턴 실측에서도 턴당 36~91초였다. **클라이언트 타임아웃도 "끊김"으로 보인다.** 그리고 섹션 17의 상류 이슈가 지적하듯 **클라이언트가 끊어도 상류 생성은 취소되지 않는다.**

#### D-6. 해법 검증

**① `think: false` — 압도적이다 (Ollama 직접, 3회씩)**

| 조건 | eval_count | thinking | 소요 |
|---|---|---|---|
| **`think: false`** | **3 · 3 · 3** | **0자** | **0~5초** |
| 기본(thinking 켬) | 438 · 515 · **2,631** | 최대 11,411자 | 19s · 22s · **118초** |

**같은 답('미르')을 내는데 2,631토큰 118초 vs 3토큰 0초.** 사고를 끄는 것만으로 문제가 사라진다.
🔴 그러나 **게이트웨이 경유로는 도달 불가**다(섹션 17). `think` 는 네이티브 `/api/chat` 필드이고 Bifrost 는 `/v1/*` 만 쓴다.

**② Modelfile 로 `num_ctx` 를 올린다 — 게이트웨이와 무관하게 동작한다**

```
FROM qwen3.5:9b
PARAMETER num_ctx 32768
```

| 확인 | 결과 |
|---|---|
| 요청에 옵션 없이 호출 | `context_length=32768` |
| VRAM | 6.62GB / **100% GPU** |

**요청이 아무것도 보내지 않아도 적용된다.** 게이트웨이가 `num_ctx` 를 버려도 무관하다.

### 실험 E — 임베딩 모델과의 VRAM 경합 (가설 반증)

D-6 에서 `num_ctx=32,768` 을 권했으나, 그것이 `bge-m3` 와의 경합을 악화시킬 수 있다고 우려했다. **측정 결과 그 우려는 틀렸다.**

채팅 모델과 임베딩 모델을 번갈아 호출하며 `load_duration` 을 측정했다.

| 단계 | `num_ctx=4,096` | `num_ctx=32,768` |
|---|---|---|
| 1) chat 최초 적재 | load 4.9s · 상주 `qwen3.5:9b` 5.65GB | load 5.1s · 상주 `qwen3.5:9b` 6.62GB |
| 2) embed 호출 | 4.8s · 상주 **`bge-m3` 만** 0.66GB | 4.2s · 상주 **`bge-m3` 만** 0.66GB |
| 3) chat 재호출 | **load 5.6s** · 상주 `qwen3.5:9b` | **load 5.6s** · 상주 `qwen3.5:9b` |
| 4) embed 재호출 | 3.8s | 3.8s |
| 5) chat 재호출 | **load 5.8s** | **load 5.9s** |

**읽어낸 것:**

* **두 설정의 동작이 같다.** `num_ctx` 를 8배로 올려도 경합이 나빠지지 않는다 → **D-6 조치 1을 막을 이유가 없다.**
* 🔴 **그런데 경합은 이미 일어나고 있다.** 4,096 에서도 채팅↔임베딩 전환마다 모델이 **퇴거되고 약 5초를 들여 재적재**된다.
* **VRAM 부족 때문이 아니다.** 4,096 일 때 5.65 + 0.66 = **6.31GB** 로 실효 예산(약 6.7GB) 안에 들어간다. 그런데도 한 번에 하나만 상주한다 → **용량이 아니라 적재 정책 문제다.**
* **위키 파이프라인은 생성과 임베딩을 번갈아 쓴다.** 즉 이 5초는 매 전환마다 조용히 지불되고 있는 **숨은 지연**이다. 지금까지 아무도 재지 않았다.

**후보 조치(미검증):** `OLLAMA_MAX_LOADED_MODELS` 가 설정돼 있지 않다. 값을 2 이상으로 두면 둘이 함께 상주할 수 있는지 확인할 가치가 있다. **다만 Ollama 재시작이 필요해 이번에는 시도하지 않았다.**

### 결론

#### 근본 원인 — "2~3턴 뒤 끊김"의 연쇄

1. 실효 컨텍스트가 **4,096** 에 고정돼 있다. Ollama 기본값이고, **게이트웨이가 `num_ctx` 를 버려 올릴 방법이 없다.**
2. `qwen3.5:9b` 는 thinking 모델이고 **사고 길이가 428~4,058 토큰으로 크게 흔들린다.**
3. 턴이 쌓이면 히스토리가 예산을 갉아먹어 **사고에 쓸 수 있는 여유가 줄어든다.**
4. 사고가 남은 예산을 넘으면 `done_reason=length` 로 끊기고 **본문이 빈 채로 반환된다.** 한계 전이라도 사고만 하고 끝내는 경로가 따로 있다.
5. 사고가 길면 응답이 **90~120초**가 되어 **클라이언트 타임아웃**이라는 두 번째 끊김 경로가 생긴다.

**하드웨어는 32,768 까지 버티는데 운영은 그 1/8 을 쓰고 있었다.** 상한이 모자라서가 아니라, **설정이 하드웨어 여유에 도달하지 못하고 있었다.**

#### 권장 조치 — 순서대로

| 순서 | 조치 | 효과 | 게이트웨이 의존 |
|---|---|---|---|
| **1** | `qwen3.5:9b` 파생 모델에 **`PARAMETER num_ctx 32768`** | 예산 8배. (a) 경로 실질 제거 | **없음 — 즉시 가능** |
| **2** | 짧은 답이 필요한 용도는 **thinking 아닌 모델**로 라우팅 | `qwen2.5-coder:7b` 는 같은 질문에 171토큰 | 없음 |
| **3** | 클라이언트 타임아웃을 **150초 이상**으로 | (2)의 끊김 경로 차단 | 없음 |
| **4** | `think: false` 도달 경로 확보 = **게이트웨이 전환** | 근본 해결. 2,631토큰 → 3토큰 | **LiteLLM 필요** |

**1~3 은 지금 바로 할 수 있고, 4 만 게이트웨이 전환이 필요하다.**

#### 이 결과가 게이트웨이 전환 판단에 주는 것

`Docs/troubleshooting.md` 섹션 17 분석에서 전환 트리거를 *"thinking 폭주가 실제 문제로 드러나면"* 으로 잡아 두었다. **드러났다.** 다만 성격이 다르다.

* 1~3 으로 **증상은 상당 부분 완화된다.** 즉 전환이 급하지는 않다.
* 그러나 **원인은 남는다.** 사고 자체를 끄지 못하는 한 매 호출에 수백~수천 토큰의 사고 비용을 계속 지불한다. `think: false` 가 그것을 3토큰으로 만든다는 것이 실측됐다.
* **판단 재료가 바뀌었다** — 전환의 가치가 "이론적 정합성"에서 **"측정된 118초 대 0초"** 로 구체화됐다.

#### 아직 측정하지 않은 것

| 항목 | 왜 필요한가 |
|---|---|
| **`num_ctx=32768` 적용 후 빈 응답 재발률** | 조치 1의 효과를 사후 확인해야 한다. 사고 폭증 자체는 남으므로 완전 제거가 아니다 |
| 턴별 실패율 | D-4 의 인과는 추론이다. 직접 세지 않았다 |
| ~~`bge-m3` 동시 상주 여부~~ | **실험 E 에서 측정 완료 — 우려는 기각됐다.** 경합은 `num_ctx` 와 무관하며 이미 발생 중이다. 대신 `OLLAMA_MAX_LOADED_MODELS` 검증이 새 과제로 남았다 |
| `exaone3.5:7.8b` · `phi4` 의 thinking 여부 | 조치 2의 라우팅 대상 선정에 필요 |

> 세 번째 항목은 **실험 E 에서 측정했고 기각됐다.** 조치 1을 막을 이유가 없다. 대신 **별개의 숨은 비용**(전환마다 약 5초 재적재)이 드러났고, 이는 `num_ctx` 와 무관하게 지금도 지불되고 있다.

## 8. 게이트웨이 아키텍처 재검토 (2026-08-22)

> 실험 D-6 의 조치 4(`think: false` 도달을 위한 게이트웨이 전환)를 두고, **"LiteLLM 은 공급자 공격으로 보안 문제가 있었다"** 는 지적과 **"차라리 에디터에서 멀티 오케스트레이션을 하면 어떤가"** 라는 제안이 나왔다. 둘 다 검토한다.

### 8-1. LiteLLM 보안 이력 — 앞선 권고를 철회한다

`troubleshooting.md` 섹션 17 분석에서 대안 게이트웨이로 LiteLLM 을 들었다. **그때 보안 이력을 확인하지 않은 것이 분석의 공백이었다.** 지적이 타당했다.

**① 공급망 침해 — CVE-2026-33634**

| 항목 | 내용 |
|---|---|
| 침해 버전 | PyPI `litellm==1.82.7` · `1.82.8` |
| 노출 시간 | 2026-03-24, 약 40분 |
| 악성 동작 | 환경변수 · SSH 키 · 클라우드 자격증명(AWS/GCP/Azure) · 쿠버네티스 토큰 · DB 비밀번호 탈취 후 비공식 도메인으로 유출 |
| 침입 경로 | **Trivy** 의 GitHub Actions 파이프라인 침해 → LiteLLM 이 CI 에서 Trivy 를 쓰고 있었음 → PyPI 배포 토큰 탈취 |
| 영향 규모(보도) | 2,500+ 조직 · 43만+ CI/CD 파이프라인 |
| 대응 | 패키지 회수, 자격증명 교체, Mandiant 포렌식, CI/CD v2 재구축, v1.83.0 부터 cosign 이미지 서명 |
| 현재 지침 | **v1.83.0 이상 사용.** v1.78.0~v1.82.6 은 감사 완료 · 클린. **공식 Docker 이미지 사용자는 영향 없음** |

**② 프록시 SQL 인젝션 — CVE-2026-42208**

* LiteLLM 프록시의 SQL 인젝션, **심각도 9.3**.
* **공개 후 36시간 내에 실제 악용**이 관측됐다.

**판단:**

* 공급망 건만 놓고 보면 **대응은 적절했고**, 우리가 쓰게 될 **Docker 경로는 애초에 영향받지 않았다.** 이 건 하나로 배제할 근거는 약하다.
* 그러나 **CVE-2026-42208(9.3)은 제품 자체의 보안 성숙도 신호**다. 게이트웨이는 **모든 프로바이더 키를 쥐는 단일 지점**이므로 일반 라이브러리보다 기준이 높아야 한다.
* → **"LiteLLM 으로 전환" 권고를 철회한다.** 전환 자체를 영구 배제하자는 것이 아니라, **`think` 하나 때문에 키를 쥔 네트워크 서비스를 통째로 갈아끼우는 것은 비용 대비 위험이 크다**는 뜻이다.

> **함께 남길 것:** Bifrost 가 더 안전하다는 근거도 우리에겐 없다. 같은 종류의 위험을 같은 방식으로 안고 있다. **줄일 수 있는 것은 "키를 쥔 네트워크 서비스의 개수"다.** 이것이 8-3 의 출발점이다.

### 8-2. Orca 같은 에디터 오케스트레이션 — 부분적으로만 대안이다

**Orca** 는 코딩 에이전트를 병렬로 돌리는 데스크톱 도구다(MIT, 2026-03 첫 안정판). 워크트리를 격리해 여러 에이전트를 동시에 굴리고 모바일에서 확인하는 구조다. 같은 이름의 프로젝트가 여럿 있어 혼동하기 쉽다 — 멀티롤 오케스트레이션 런타임, 에이전트 DSL 등도 있다.

**핵심 차이는 "사람이 앞에 있는가"다.**

| | 에디터 오케스트레이션 | 이 프로젝트의 LLM 트래픽 |
|---|---|---|
| 성격 | **대화형(attended)** — 개발자가 지시하고 결과를 본다 | **무인(unattended)** |
| 실행 주체 | 사람이 연 세션 | `wiki_agent.py` (pythonw 백그라운드 데몬) · `discord_bot.py` · CI 잡 |
| 트리거 | 사람의 입력 | 볼트 파일 변경 · 디스코드 메시지 · PR 이벤트 |

**따라서 직접 대체 관계가 아니다.** 에디터 오케스트레이터는 **사람이 없으면 아무것도 하지 않는다.** 위키 자동 정제 파이프라인을 대신할 수 없다.

**다만 유효한 영역이 분명히 있다.** 지금 하고 있는 것 같은 **다중 모델 비교 · 프롬프트 실험 · 코드 작업**은 에디터 오케스트레이션 쪽이 낫다. 이 부분은 애초에 게이트웨이가 풀던 문제가 아니었다.

### 8-3. 더 중요한 질문 — 이 프로젝트에 게이트웨이가 필요한가

지적을 따라가다 보면 진짜 질문은 "어느 게이트웨이냐"가 아니라 **"게이트웨이가 이 경로에 필요한가"** 다. 게이트웨이가 실제로 주는 것을 하나씩 보면 **대부분 이미 다른 곳에 있다.**

| 게이트웨이 기능 | 이미 있는 대안 | 평가 |
|---|---|---|
| 다중 프로바이더 라우팅 | 코드가 이미 `langchain_openai.ChatOpenAI` 를 쓴다. LangChain 은 Ollama · Gemini · Anthropic 등을 **직접** 지원 | **중복** |
| Langfuse 관측 | LangChain **콜백으로 네이티브 지원** | **중복** |
| Open WebUI 백엔드 | **Open WebUI 는 Ollama 를 네이티브로 직접 지원한다** | **로컬 한정 중복** |
| 키 단일 관리 | `.env` + `config.py` (이미 있음) | 중복 |

그리고 결정적으로 — **게이트웨이가 바로 문제의 원인이다.** 이번 조사에서 측정된 것:

* `max_tokens` · `max_completion_tokens` 버림 (섹션 17)
* **`num_ctx` 버림** (D-1) → 실효 컨텍스트가 4,096 에 고정
* `think` 도달 불가 (D-6)

**Ollama 직접 호출에는 이 문제가 하나도 없다.** 셋 다 정확히 동작하는 것을 실측했다.

### 8-4. 제안 — 게이트웨이를 없애지 말고, 문제가 생기는 경로만 뺀다

| 경로 | 방식 | 근거 |
|---|---|---|
| **로컬 모델 · 무인 파이프라인** (`wiki_agent` · `fastapi_wiki_server`) | **Ollama 직접 호출** — `src/llm_client.py` 팩토리 | `num_ctx` · `num_predict` · `think` 전부 제어 가능. **측정된 문제가 전부 사라진다** |
| **로컬 모델 · 대화** (Open WebUI) | **Open WebUI → Ollama 직접** | 네이티브 지원. 게이트웨이를 거칠 이유가 없다 |
| **클라우드 프로바이더** (gemini · groq · cerebras · mistral · anthropic) | 게이트웨이 유지 | 여기서는 결함이 문제되지 않을 가능성이 높다. **단 미측정** — #5606 이 custom openai-compat 전반을 다루므로 확인 필요 |
| **개발 · 실험 · 코드 작업** | Orca 같은 도구 | 대화형 작업에 적합. 애초에 게이트웨이 영역이 아니다 |

**이 방식의 장점:**

1. **키를 쥔 네트워크 서비스가 줄지 않지만, 그 서비스를 지나는 트래픽이 준다.** 로컬 모델 호출은 아예 게이트웨이를 안 거친다.
2. **변경 범위가 작다.** 이미 `src/chroma_client.py` 팩토리 패턴이 있으므로 `src/llm_client.py` 를 같은 방식으로 만들면 된다. 소비처는 팩토리 하나만 본다.
3. **게이트웨이 교체보다 위험이 낮다.** 클라우드 라우팅과 Langfuse 를 건드리지 않는다.
4. **D-6 의 조치 1~4 를 전부 흡수한다.** `num_ctx` 도, `think: false` 도 직접 호출이면 그냥 된다.

**대가:**

* 로컬 모델 호출의 Langfuse 추적을 잃는다 → LangChain 콜백으로 되살려야 한다. **추가 작업이 필요하다.**
* 로컬/클라우드 경로가 갈라져 코드가 두 갈래가 된다. 팩토리로 감싸면 소비처는 모르지만 **팩토리 자체는 복잡해진다.**

### 8-5. 정리

* **LiteLLM 전환 권고는 철회한다.** 지적이 타당했다.
* **에디터 오케스트레이션은 무인 파이프라인의 대안이 아니다.** 다만 개발·실험 영역에서는 별도로 검토할 가치가 있다.
* **가장 나은 선택지는 게이트웨이 교체도 유지도 아니라, 로컬 모델 경로만 직접 호출로 빼는 것으로 보인다.** 측정된 문제 셋을 한 번에 없애면서 변경 범위가 가장 작다.
* **다음에 확인할 것:** ① 클라우드 프로바이더도 같은 결함의 영향을 받는지 ② Langfuse 를 LangChain 콜백으로 옮기는 비용 ③ `OLLAMA_MAX_LOADED_MODELS` (실험 E)

## 9. 게이트웨이의 실제 역할 — 코드로 확인한 정의 (2026-08-22)

> 8장의 제안을 판단하려면 **게이트웨이가 실제로 무엇을 하고 있는지**부터 확정해야 한다. 설계 의도가 아니라 **배포된 상태**를 기준으로 전수 조사했다.

### 9-1. 게이트웨이를 지나는 트래픽 — 전수 3곳, 런타임은 1곳

| 소비처 | 위치 | 성격 |
|---|---|---|
| `ChatOpenAI(base_url=BIFROST_BASE_URL)` | `src/agent/wiki_agent.py:176` | **유일한 런타임 소비처** |
| PR 영향 분석 | `scripts/impact_analysis.py:34` | CI 전용 |
| 성능 벤치마크 | `scripts/benchmark_bifrost.py:98` | CI 전용 |

### 9-2. 게이트웨이를 지나지 **않는** 것 — 이미 직접 호출 중이다

| 경로 | 실제 대상 | 근거 |
|---|---|---|
| `wiki_agent` 임베딩 | **Ollama 직접** | `wiki_agent.py:163` — `OllamaEmbeddingFunction(url=f"{OLLAMA_BASE_URL}/api/embeddings")` |
| FastAPI 툴 서버 | **Ollama 직접.** 그리고 **LLM 호출 자체가 없다** | `fastapi_wiki_server.py:31` — 임베딩만 사용 |
| **Open WebUI 대화** | **Ollama 직접** | 컨테이너 env: `OLLAMA_BASE_URL=http://host.docker.internal:11434`, **`OPENAI_API_BASE_URL=` (빈 값)** |
| `discord_bot` | LLM 미사용 | 참조 0건 |

> 🔴 **설계 의도와 실제 배포가 다르다.** 시작 스크립트 주석은 Bifrost 를 *"Langfuse/OpenWebUI 연동 게이트웨이"* 라고 적고 있지만, **Open WebUI 는 Bifrost 를 거치지 않는다.** N15("낡은 문서를 근거로 삼지 말 것")가 또 한 번 적용되는 사례다.

### 9-3. 그래서 게이트웨이가 실제로 하는 일은 네 가지다

| # | 역할 | 실제 수혜 범위 |
|---|---|---|
| 1 | **모델명 → 프로바이더 라우팅** | `wiki_agent` 1곳 + CI 2곳 |
| 2 | **클라우드 프로바이더 키 보관** — `GEMINI` · `GROQ` · `CEREBRAS` · `MISTRAL` · `ANTHROPIC` 키를 컨테이너 env 로 주입 | 앱이 클라우드 키를 몰라도 됨 |
| 3 | **OpenAI 호환 단일 엔드포인트** — 소비처가 `langchain_openai` 하나로 통일 | 코드 단순화 |
| 4 | **인증 경계** — `BIFROST_API_KEY` | Ollama 자체는 무인증 |

**Langfuse 는 이 목록에 없다.** 9-5 참조 — 이미 앱 쪽에서 돌고 있다.

### 9-4. 🔴 중요한 정정 — "대화 끊김"은 게이트웨이 경로가 아니다

D-1 에서 *"Bifrost 가 `num_ctx` 를 버려 실효 컨텍스트가 4,096 에 고정된다"* 고 기록했다. 그 사실 자체는 맞다. **그러나 대화 끊김이 나는 경로에는 적용되지 않는다.**

* 대화는 **Open WebUI** 에서 이뤄지고, Open WebUI 는 **Ollama 를 직접** 부른다.
* 그 경로의 4,096 은 **Bifrost 탓이 아니라 Ollama 자체 기본값**이다.

**의미가 크다 — 이 증상은 게이트웨이를 어떻게 하든 무관하게 고칠 수 있다.** 선택지가 늘어난다.

| 방법 | 적용 범위 | 게이트웨이 의존 |
|---|---|---|
| Open WebUI 의 모델별 고급 설정에서 컨텍스트 길이 지정 | 그 대화만 | 없음 |
| `OLLAMA_CONTEXT_LENGTH` 환경변수 (시작 스크립트) | **전 모델·전 경로** | 없음 |
| Modelfile `PARAMETER num_ctx` (D-6 ② 검증 완료) | 그 파생 모델만 | 없음 |

> `OLLAMA_CONTEXT_LENGTH` 는 가장 단순하지만 **전 모델에 적용된다.** 8GB VRAM 에서 `deepseek-r1:14b` 같은 모델까지 큰 KV 캐시를 잡으면 CPU 분할이 심해질 수 있다. **모델별로 제어되는 Modelfile 쪽이 안전하다.**

### 9-5. Langfuse — "LangChain 콜백으로 옮긴다"는 표현은 틀렸다. 이미 그렇게 돌고 있다

8-4 에서 *"로컬 모델 호출의 Langfuse 추적을 잃는다 → LangChain 콜백으로 되살려야 한다"* 고 적었다. **확인 결과 이미 앱에서 콜백으로 동작 중이다.**

```python
# src/agent/wiki_agent.py
from langfuse import get_client            # :30
from langfuse.langchain import CallbackHandler   # :31
...
lf_client = get_client()                   # :353  수동 generation 기록
...
lf_handler = CallbackHandler()             # :631
final_state = app.invoke(initial_state, config={"callbacks": [lf_handler], "run_name": file_name})   # :632
```

**용어 정리 — 관측 데이터가 Langfuse 로 가는 경로는 두 가지다.**

| 경로 | 누가 보내나 | 무엇이 보이나 |
|---|---|---|
| **앱 콜백 (현재 동작 중)** | LangChain 이 실행 중 `CallbackHandler` 를 호출 → Langfuse SDK 가 전송 | LangGraph 노드 구조, 각 단계 입출력, 파일명 같은 **애플리케이션 맥락** |
| **게이트웨이 전송** | Bifrost 컨테이너가 `LANGFUSE_BASE_URL` · `LANGFUSE_AUTH_B64` 로 직접 전송 | 게이트웨이를 지난 **HTTP 요청 단위** — 모델, 토큰 수, 지연 |

**즉 "옮긴다"가 아니라 "둘 중 하나가 없어진다"가 정확한 표현이다.**

* 로컬 모델 호출을 게이트웨이에서 빼면 → **게이트웨이 전송분만 사라진다.**
* **앱 콜백은 그대로 남는다.** LangGraph 트레이스, 노드별 입출력, 파일명 맥락은 유지된다.
* 잃는 것은 **게이트웨이 관점의 요청 기록**(토큰 수·지연 집계)이다. 다만 그 정보는 LangChain 콜백에서도 상당 부분 얻을 수 있다.

→ **8-4 에 적은 "추가 작업이 필요하다"는 과대평가였다.** 실제로는 거의 없거나 작다.

### 9-6. `OLLAMA_MAX_LOADED_MODELS` — 무엇을 확인하려는 것인가

**확인하려는 것:** 실험 E 에서 관측된 **채팅↔임베딩 전환마다 약 5초 재적재**가, **VRAM 이 부족해서인가 아니면 Ollama 의 적재 정책 때문인가.**

**왜 정책 문제로 의심하는가:**

* `num_ctx=4,096` 일 때 `qwen3.5:9b` 5.65GB + `bge-m3` 0.66GB = **6.31GB**
* 실효 VRAM 예산은 약 **6.7GB** (실험 A 에서 두 번의 분할 지점이 6.66GB · 6.77GB)
* **즉 둘이 함께 올라갈 여유가 있는데도 한 번에 하나만 상주한다.**

`OLLAMA_MAX_LOADED_MODELS` 는 Ollama 가 동시에 메모리에 유지할 모델 수의 상한이다. **현재 설정돼 있지 않다**(시작 스크립트는 `OLLAMA_NUM_THREADS=6` 만 설정).

| 결과 | 해석 | 후속 |
|---|---|---|
| 값을 2 로 올렸더니 둘 다 상주 | **정책 문제였다.** 환경변수 한 줄로 전환당 5초를 없앤다 | 시작 스크립트에 추가 |
| 올려도 여전히 퇴거 | Ollama 의 VRAM 추정이 보수적이거나 다른 제약 | 전환 비용을 상수로 받아들이고 파이프라인 설계에 반영 |

**검증에 Ollama 재시작이 필요해 이번에는 하지 않았다.** 환경변수는 프로세스 시작 시점에만 읽히기 때문이다.

> **이 값이 중요한 이유:** 위키 파이프라인은 생성과 임베딩을 번갈아 쓴다. 전환이 문서 한 건당 여러 번 일어난다면 **5초 × 전환 횟수**가 누적된다. 지금까지 아무도 재지 않은 비용이다.

## 10. 게이트웨이를 클라우드 전용으로 좁히면 — 문제와 부작용

> 8-4 의 제안을 실행한다고 가정하고, **잃는 것과 새로 생기는 것**을 정리한다.
> 9장에서 확인했듯 **실제 변경 대상은 `wiki_agent.py:176` 한 줄**이다(임베딩·Open WebUI·discord bot 은 이미 게이트웨이를 안 거친다).

### 10-1. 실제로 바뀌는 것

```python
# 현재 — src/agent/wiki_agent.py:176
llm = ChatOpenAI(model=settings.MODEL_NAME, base_url=settings.BIFROST_BASE_URL,
                 api_key=settings.BIFROST_API_KEY, temperature=0.1)
```

로컬 모델일 때는 Ollama 를 직접 부르고, 클라우드 모델일 때만 게이트웨이로 보내는 팩토리(`src/llm_client.py`)로 감싼다.

### 10-2. 문제와 부작용

| # | 항목 | 내용 | 심각도 |
|---|---|---|---|
| 1 | **라우팅 분기 기준이 새로 필요하다** | `settings.MODEL_NAME` 하나로 로컬/클라우드를 판단할 근거가 없다. 모델명 규칙(`:` 포함 여부 등)은 취약하고, 별도 목록이나 설정이 필요하다. **이 판단이 틀리면 조용히 엉뚱한 경로로 간다** | 🔴 높음 |
| 2 | **`temperature` 등 파라미터 이름·의미 차이** | `ChatOpenAI(temperature=0.1)` 과 Ollama 네이티브 `options.temperature` 는 이름은 같아도 전달 경로가 다르다. **`langchain_ollama` 를 쓰면 LangChain 이 흡수하지만, 직접 호출하면 매핑을 직접 져야 한다** | 🟡 중간 |
| 3 | **의존성이 늘어난다** | `langchain_ollama` 추가. `requirements.txt` 갱신, CI 재설치 | 🟢 낮음 |
| 4 | **폴백 체인을 잃을 수 있다** | 게이트웨이에 폴백이 설정돼 있다면 로컬 경로에서 사라진다. **현재 설정 여부는 미확인** — configstore 를 봐야 한다 | 🟡 미확인 |
| 5 | **인증 경계가 사라진다** | 게이트웨이는 `BIFROST_API_KEY` 로 보호되지만 **Ollama 는 무인증**이고 `OLLAMA_HOST=0.0.0.0` 으로 전 인터페이스에 열려 있다. 다만 **임베딩·Open WebUI 가 이미 그 경로를 쓰고 있으므로 새로 생기는 노출은 없다** | 🟡 기존 위험 |
| 6 | **벤치마크의 의미가 바뀐다** | `benchmark_bifrost.py` 는 "운영 경로"를 재는 것이 목적이다. 운영이 Ollama 직접으로 바뀌면 **벤치마크도 그 경로를 재야 한다.** 안 바꾸면 아무도 안 쓰는 경로를 측정하게 된다 | 🟡 중간 |
| 7 | **Langfuse 게이트웨이 전송분을 잃는다** | 9-5 참조. **앱 콜백은 그대로 남으므로 손실이 작다** | 🟢 낮음 |
| 8 | **코드가 두 갈래가 된다** | 팩토리로 감싸면 소비처는 모르지만 **팩토리 자체는 분기를 안게 된다.** 유지보수 지점이 하나 늘어난다 | 🟢 낮음 |
| 9 | **게이트웨이의 존재 이유가 얇아진다** | 남는 트래픽이 CI 2곳 + 클라우드 호출뿐이다. **"이 컨테이너를 계속 돌릴 가치가 있는가"라는 질문이 뒤따른다** | 🟡 판단 필요 |

### 10-3. 반대로 **생기지 않는** 문제 — 오해하기 쉬운 것

| 오해 | 실제 |
|---|---|
| "Open WebUI 대화가 끊긴다" | **이미 게이트웨이를 안 거친다.** 영향 없음 |
| "임베딩 검색이 깨진다" | **이미 Ollama 직접이다.** 영향 없음 |
| "Langfuse 관측을 잃는다" | 앱 콜백은 유지된다. 게이트웨이 전송분만 사라진다 |
| "클라우드 라우팅을 다시 짜야 한다" | 그대로 둔다. 로컬 경로만 분기한다 |

### 10-4. 판단

**1번(라우팅 분기 기준)이 유일한 실질적 난점**이고 나머지는 작거나 이미 존재하는 위험이다. 분기 기준을 **명시적 설정**(예: `.env` 에 로컬 모델 목록)으로 두면 1번도 관리 가능하다.

**다만 9-4 의 정정을 감안하면 우선순위가 내려간다** — 대화 끊김은 게이트웨이와 무관하게 고칠 수 있으므로, **이 변경은 "증상 해결"이 아니라 "구조 정리"의 성격**이다. 급하지 않다.

## 11. Orca 도입 판단 기준

> "쓸까 말까"를 감으로 정하지 않도록, **무엇을 대체하려는지에 따라** 기준을 나눈다.

### 11-1. 1차 판별 — 무인 파이프라인의 대안으로 검토하는가

**아래 중 하나라도 "예"면 Orca 는 대안이 아니다.**

| 질문 | 이 프로젝트 |
|---|---|
| 실행 트리거가 사람이 아닌가? (파일 변경 · 웹훅 · 스케줄 · CI 이벤트) | **예** — 볼트 파일 변경, 디스코드 메시지, PR 이벤트 |
| 사람이 없을 때도 돌아야 하는가? | **예** — `pythonw` 백그라운드 데몬 |
| 실패 시 자동 알림·재시도가 필요한가? | **예** — `wiki_agent.py:159` 웹훅 알림 |
| 결과물이 사람의 확인 없이 저장되는가? | **예** — 위키 문서 자동 생성 |

→ **위키 파이프라인의 대체재로는 부적합하다.** 에디터 오케스트레이터는 사람이 세션을 열어야 동작한다.

### 11-2. 2차 판별 — 개발·실험 도구로 검토하는가

**아래를 만족할수록 도입 가치가 있다.**

| 기준 | 판단 근거 |
|---|---|
| 여러 에이전트를 **병렬로** 돌릴 일이 실제로 있는가 | 없다면 단일 에이전트로 충분하다. 병렬 격리(worktree)가 Orca 의 핵심 가치다 |
| 작업이 **코드 변경** 중심인가 | Orca 는 코딩 에이전트 오케스트레이터다. 프롬프트 튜닝·문서 작업 중심이면 이득이 작다 |
| **클라우드 구독**을 쓰는가, 로컬 모델을 쓰는가 | Orca 계열은 구독 기반 코딩 에이전트를 전제로 설계됐다. **로컬 Ollama 모델을 붙이는 것은 별도 확인이 필요하다** |
| 결과를 **사람이 검토**하고 병합하는가 | 그렇다면 적합. 무인 자동 병합이면 부적합 |
| 도입·학습 비용을 감당할 여유가 있는가 | 릴리스가 잦은 신생 도구다. 운영 안정성보다 실험 성격이 강하다 |

### 11-3. 배제 기준 — 이것 때문에 도입하면 안 된다

* ❌ **"게이트웨이 문제를 해결하려고"** — Orca 는 토큰 상한·컨텍스트 문제와 **아무 관계가 없다.** 이번 조사에서 나온 문제를 하나도 풀지 못한다.
* ❌ **"Bifrost 대신"** — 대체 관계가 성립하지 않는다(11-1).
* ❌ **"LiteLLM 이 위험하니 대신"** — 해결하려는 문제가 다르다. 보안 우려의 답은 **키를 쥔 서비스를 줄이는 것**(10장)이지 다른 도구를 얹는 것이 아니다.

### 11-4. 결론

**두 질문은 분리해서 답해야 한다.**

| 질문 | 답 |
|---|---|
| 게이트웨이 대안으로 Orca 를 쓸 것인가 | **아니오.** 성격이 다르고 이번 문제를 풀지 못한다 |
| 개발 워크플로 도구로 Orca 를 도입할 것인가 | **별건으로 검토할 가치가 있다.** 11-2 기준으로 판단하되, **이번 조사와는 무관한 결정**이다 |
