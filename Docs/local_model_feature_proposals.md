## 0. 문제 정의 — 모델 능력과 실제 사용량의 격차

2026-10-15 라이브 점검(`ollama show`) 결과, 보유 모델의 능력이 실사용을 크게 앞선다.

| 모델 | 실측 capabilities | 네이티브 ctx | 프로젝트가 실제로 쓰는 범위 |
|---|---|---|---|
| `gemma4:e4b` | completion · vision · **audio** · tools · thinking | 131,072 | 텍스트 단발 호출만 (`temperature=0.1`) |
| `qwen3.5:9b` | completion · vision · tools · thinking | 262,144 | Open WebUI 수동 채팅만 |
| `qwen2.5-coder:7b` | completion · tools · **insert** | 32,768 | 벤치마크만 |

**즉 vision · audio · tools · thinking 네 가지가 전부 유휴 상태다.** 로컬 모델을 호출하는
코드 경로는 `wiki_agent.py` 의 classify → clean → compile 과 `embedding_function.py` 둘뿐이다.

> **`insert` 는 `qwen2.5-coder:7b` 만 가진 능력이다** — 이것이 FIM(fill-in-the-middle,
> 탭 자동완성)의 실체다. `gemma4:e4b` · `qwen3.5:9b` 의 capabilities 에는 `insert` 가 **없다.**
> 2024년 모델인 `qwen2.5-coder` 를 계속 두는 이유가 이것이며, 신형 범용 모델로 대체되지 않는다.

가장 큰 구조적 결손은 **프라이버시 경계가 설계상으로만 존재한다는 점**이다 —
[`implementation_plan.md`](implementation_plan.md) 4-2 는 `#personal` · 이력서 · 회고를
**로컬 전용**으로 못박았으나, 정작 그 데이터를 질의할 로컬 기능이 없다. 아래 ① 이 이것을 메운다.

### 권장 착수 순서

확정 순서와 근거는 [7장](#확정-착수-순서)에 정리했다. 요지는 **⑤(계측)를 가장 먼저** 하는 것이다 —

## ① 로컬 툴 콜링 에이전트 — 최우선

### 현재 상태
`src/tools/fastapi_wiki_server.py` 는 **Open WebUI 의 OpenAPI 툴로만** 연결돼 있다.
사람이 Open WebUI 에서 모델을 고르고 질문해야 위키 검색이 돈다 —
**로컬 모델이 스스로 위키를 검색하는 경로가 없다.**

### 제안
`gemma4:e4b` / `qwen3.5:9b` 의 네이티브 tool calling 으로 LangGraph ReAct 에이전트를 구성한다.

```
사용자 질의
   │
   ▼
[LangGraph ReAct 루프]  ← 로컬 모델 (tools 지원)
   │  ├─ tool: wiki_search(query)        → ChromaDB 벡터 검색
   │  ├─ tool: wiki_read(doc_id)         → Obsidian 원문 읽기
   │  └─ tool: wiki_list_by_tag(tag)     → 태그별 목록
   ▼
종합 답변 (멀티스텝)
```

* 기존 `fastapi_wiki_server.py` 의 검색 로직을 **LangChain `@tool` 로 재노출**한다 —
  엔드포인트를 새로 만들지 말고 함수를 공유해 로직 중복을 피한다.
* 모델 호출은 기존대로 Bifrost 경유 → Langfuse 트레이싱이 멀티스텝 루프까지 자동 포착된다.
* thinking 지원 모델이므로, 도구 선택 단계에서만 thinking 을 켜고 최종 답변에선 끄는 분기가 가능하다.

### ✅ 1-1. 착수 전 기획 수정 — 도구 사양 확정 (2026-10-17)

구현 전 실제 데이터를 조사한 결과 **기존 도구 2종을 그대로 쓸 수 없다**는 것이 확인됐다.
에이전트는 사람과 달리 도구 출력을 **사실로 믿고 추론**하므로, 틀린 전제를 주는 도구는
사람이 쓸 때보다 훨씬 해롭다.

#### 조사 결과 (실측, 2026-10-17)

| 항목 | 값 |
|---|---|
| ChromaDB | **청크 37개 / 문서 9개** |
| 메타데이터 키 | **`source`, `category` 둘뿐 — 날짜 필드가 아예 없다** |
| 문서 id 형태 | `{source}_chunk_{N}` |
| Vault 파일 | tech 6개 · **career 0개 · personal 0개** |
| 드리프트 | **DB 9개 중 4개가 vault 에 대응 파일이 없다 (44%)** |

#### 발견한 결함 3가지

1. 🔴 **`get_recent_wiki_titles` 는 "최근"을 돌려줄 수 없다.** 메타데이터에 날짜가 없고
   `collection.get(limit=N)` 은 ChromaDB 의 임의/삽입 순서다. 날짜 정렬이 **불가능**하다.
2. 🔴 **`limit` 의 단위가 문서가 아니라 청크다.** `get(limit=10)` → source 중복 제거 → 슬라이스
   순서라, `limit=10` 이 문서 10개를 보장하지 않는다(문서당 청크가 1~11개로 들쭉날쭉하다).
3. 🔴 **드리프트 4건.** 그중 하나는 **같은 문서가 이름만 달라 양쪽에 중복 계수**된 것이다 —
   vault 파일명에는 `[[Discord_20260724_120800.md]]`, DB `source` 에는 `.md` 가 빠진 형태로
   들어가 있다. 즉 **`source` 문자열로 vault↔DB 를 조인하는 설계는 깨진다**
   (제목에 이모지·위키링크·확장자 조각이 섞여 있다).

#### ✅ 확정 사양

**방식: 색인 시점에 타임스탬프 메타데이터를 넣고 전체 재색인한다.**

Vault 파일 mtime 을 읽는 방식(파일시스템 기반)도 검토했으나 기각했다 — 위 결함 3 때문에
vault↔DB 조인이 신뢰할 수 없고, 에이전트가 "최근 문서"를 받아 곧바로 검색으로 넘어가는
흐름에서 **조인 실패가 곧 빈 검색 결과**가 된다. 재색인은 **문서 9개 / 청크 37개 규모라
비용이 사실상 없고**(`src/scripts/reembed_chroma.py` 기존 보유), 부수적으로 드리프트 4건도
함께 정리된다.

| 도구 | 변경 |
|---|---|
| `search_wiki_knowledge` | 유지. 단 내부 로직을 순수 함수로 추출해 공유 |
| ~~`get_recent_wiki_titles`~~ → **`list_wiki_documents`** | **문서 단위**로 센다. `indexed_at` 내림차순 정렬, `category` 필터 지원. `limit` 은 **문서 개수** |
| **`read_wiki_document`** (신규) | `source` 로 그 문서의 전체 청크를 순서대로 반환 — 현재는 검색이 청크 조각만 주므로 에이전트가 원문을 볼 수 없다 |

추가 메타데이터: **`modified_at`**(ISO8601) · `chunk_index`(정렬용).

> **`indexed_at` 이 아니라 `modified_at` 으로 확정한 이유.** 일괄 재색인에서 날짜를
> `now()` 로 넣으면 **전 문서가 같은 타임스탬프**가 되어 "최신순"이 다시 무의미해진다.
> 그래서 값의 출처를 **Vault 파일의 mtime** 으로 고정했고, 그러면 "색인한 시각"이 아니라
> "문서가 마지막으로 쓰인 시각"이므로 이름도 그에 맞췄다. 상시 색인
> (`wiki_agent.py`)도 같은 의미가 되도록 **방금 쓴 파일의 mtime** 을 읽는다 —
> 두 경로의 의미가 어긋나면 정렬이 섞인다.

#### ✅ 실행 완료 (2026-10-17)

`src/agent/wiki_agent.py`(상시 색인) · `src/scripts/reembed_chroma.py`(일괄) 두 경로 모두에
`modified_at` · `chunk_index` 를 추가하고 **비파괴 모드(`--prune` 없이)로 재색인했다.**

```
6개 파일 / 31개 청크 재색인 완료
modified_at 보유 31 / chunk_index 보유 31  (전체 37청크 중)
정렬 확인: 2026-08-31 > 08-10 > 07-24 > 07-24 > 07-10 > 06-29, 날짜 없는 3건은 뒤로
category='tech' 필터: 문서 9개 -> 8개 (personal 1건 차단)
```

**예상과 달랐던 점 — 고아는 4건이 아니라 3건이었다.**
`X API ... [[Discord_20260724_120800]]` 이 중복되리라 예상했으나 중복되지 않았다.
원인은 색인 코드의 `file_name.replace(".md", "")` 가 **greedy** 라는 것이다 — 파일명
`X API ... [[Discord_20260724_120800.md]].md` 에서 **안쪽 `.md` 까지 함께 지워져**
기존 DB 의 source 와 정확히 일치했다. 즉 앞서 '이름 불일치 드리프트'로 진단한 1건은
실재하지 않았고, 두 색인 경로가 같은 `.replace` 를 쓰기 때문에 일관성이 유지된다.

> ⚠️ **다만 이것은 잠복 결함이다.** 제목에 `.md` 가 들어간 문서가 생기면 source 가
> 조용히 망가진다. 지금은 두 경로가 같은 방식이라 일치하므로 동작하지만,
> `os.path.splitext` 로 바꾸는 것이 옳다 — 바꿀 때는 **두 경로를 동시에** 고치고
> 재색인해야 한다(한쪽만 고치면 source 가 갈라진다).

**고아 레코드 3건 — `--prune` 으로 삭제 완료 (2026-10-17):**

| 분류 | source | 처리 |
|---|---|---|
| 🔴 **personal** | `AI_Discord_20260724_004002` | 삭제 |
| tech | `앤트로픽 경제 지수 - 실시간 AI 사용자 데이터 분석 및 활용 가이드` | 삭제 |
| tech | `앤트로픽 클로드 - 전 세계 사용자 행동 데이터를 통한 시장 트렌드 분석` | 삭제 |

셋 다 vault 에 원본이 없었다. 삭제 후 최종 상태:

```
청크 37 -> 31,  문서 9 -> 6
modified_at 없는 청크: 0      (전 문서가 정렬 가능)
non-tech(personal) 문서: 0    (색인에 personal 잔존 없음)
```

**색인과 vault 가 완전히 일치하는 상태가 됐다.** `list_wiki_documents` 의
"날짜 미상" 경고도 더 이상 출력되지 않는다 — 경고가 필요한 문서가 없기 때문이다.

> 삭제는 옵트인(`--prune`)으로 남겨 둔다. 기본값은 꺼져 있다 — 데이터 삭제이므로
> 재색인을 돌릴 때마다 조용히 지워지면 안 된다.

#### 💡 부수 발견 — `category` 가 프라이버시 경계의 집행 수단이다

메타데이터에 **`category`('tech' 등)가 이미 있다.** 이것이 ③·⑥ 에서 "`#personal` 차단을
**코드 경로로** 보장해야 한다"고 적은 그 수단이다 — 태그를 사람의 주의에 맡기지 않고
**쿼리 필터(`where={"category": "tech"}`)로 강제**할 수 있다.

🔴 **그리고 이것은 미래의 이야기가 아니다 — `#personal` 데이터가 이미 색인돼 있다.**
도구 구현 후 실제로 돌려본 결과:

```
list_wiki_documents(limit=3)                  -> 색인된 위키 문서 9개
list_wiki_documents(limit=3, category='tech') -> 색인된 위키 문서 8개
```

차이 1건은 `AI_Discord_20260724_004002` 이고 **`category: personal`** 이다.
(`personal` *디렉터리*는 비어 있으나, 색인에는 personal 문서가 들어 있다 — 디렉터리가
비었다는 사실로 색인이 깨끗하다고 판단하면 틀린다.)

함의 두 가지:

1. **⑥ Jev 연결 시 카테고리 필터는 선택이 아니라 필수다.** 필터 없이 위키를 외부로
   보내면 **지금 당장 personal 문서가 섞여 나간다.** `category` 필터가 그것을 막는
   유일한 코드 수준 수단이며, 위 실측으로 **필터가 실제로 작동함이 확인됐다**(9→8).
2. 🔴 **고아 personal 레코드가 있다.** 이 문서는 드리프트 4건 중 하나로
   **vault 에 대응 파일이 없다** — 즉 원본은 지워졌는데 색인에만 personal 데이터가
   남아 있다. 재색인 시 정리되지만, **정리 여부는 사용자가 판단할 데이터 위생 문제다.**

이 실측으로 ⑥ 의 완료 기준("`#personal` 을 한 건도 포함하지 않음을 코드 경로로 보장")은
**구현 가능함이 확정**되는 동시에, **반드시 해야 하는 일로 격상된다.**

### 왜 지금 가능해졌는가
이전 라인업(`exaone3.5` · `phi4`)은 `capabilities` 가 `completion` 뿐이라 tool calling 이
**원천적으로 불가능**했다. 현재 라인업은 **보유 생성 모델 전부가 `tools` 를 네이티브 지원**한다
(`gemma4:e4b` · `qwen3.5:9b` · `qwen2.5-coder:7b` · `deepseek-r1:14b` 모두 실측 확인).

* 시스템 프롬프트에 "위키에 없으면 없다고 말하라"·"출처를 적으라"·
  "목록 순서를 최신순으로 단정하지 말라"를 명시

**완료 기준 검증 결과:**

질의: *"가장 최근에 수정된 문서를 목록으로 확인하고, 그 문서 전문을 읽어 3줄 요약해줘"*

```
[도구 호출 1] wiki_list args={'limit': 10}
[도구 호출 2] wiki_read args={'source': 'LSP 기반 심볼 탐색 연동 - ...'}
→ 최종 답변에 날짜(2026-08-31)와 출처를 정확히 인용
```

**도구 2회 자율 호출 확인.** 단일 검색으로 답되는 질의("Ollama 설정 내용 있어?")에서는
1회만 호출하고 끝낸다 — 불필요한 호출을 하지 않는다는 뜻이므로 정상이다.

> 💡 이 검증은 **이번 세션 작업이 사슬로 연결됨을 보여준다.** 에이전트가 날짜를 인용할 수
> 있는 것은 ①-1-1 에서 `modified_at` 을 추가했기 때문이고, 문서 전문을 읽을 수 있는 것은
> `read_wiki_document` 를 신설했기 때문이다. 메타데이터 없이는 "가장 최근" 질의 자체가
> 성립하지 않았다.

### 완료 기준

## ③ 리랭커 도입 — 상세 분석

### 3-1. 리랭커란 무엇인가

현재 RAG 검색은 **임베딩(bi-encoder) 단독**이다.

| 구분 | Bi-encoder (현재 `bge-m3`) | Cross-encoder (리랭커) |
|---|---|---|
| 처리 방식 | 질의와 문서를 **각각 따로** 벡터화 → 코사인 유사도 | 질의와 문서를 **한 쌍으로 묶어** 모델에 함께 통과 |
| 토큰 상호작용 | 없음 (벡터로 압축된 뒤 비교) | 있음 (질의 토큰 ↔ 문서 토큰 교차 어텐션) |
| 속도 | 매우 빠름 — 벡터는 미리 계산해 저장 | 느림 — 쌍마다 모델 1회 호출 |
| 전수 검색 | 가능 (ANN 색인) | **불가능** (문서 수만큼 호출해야 함) |
| 정확도 | 보통 | 높음 |

핵심은 bi-encoder 가 **질의를 보기 전에** 문서를 벡터로 압축해 버린다는 점이다. 그래서
"A 와 B 의 차이"처럼 질의 내부 관계가 중요한 검색에서 약하다. cross-encoder 는 질의와 문서를
함께 읽으므로 이 관계를 포착하지만, 전수 검색이 불가능해 **2단계로 결합해 쓴다.**

```
질의
 │
 ├─[1단계] bge-m3 벡터 검색 → top-20 (빠르고 재현율 위주)
 │
 └─[2단계] 리랭커로 20쌍 재채점 → top-5 (정확도 위주)
              │
              ▼
         LLM 컨텍스트에 top-5 만 투입
```

### 3-2. 왜 임베딩 교체보다 리랭커인가

| 선택지 | 기대 이득 | 비용 |
|---|---|---|
| `bge-m3` → `qwen3-embedding:0.6b` | MTEB 63.2 → 64.33 (**+1.1**) | **전체 재임베딩** + bge-m3 의 hybrid(sparse·multi-vector) 상실 |
| `bge-m3` → `qwen3-embedding:4b` | MTEB 69.45 | 적재 크기 초과 — 채팅 모델과 동시 상주 불가 |
| **리랭커 추가** | 최종 top-k 정확도 개선 (일반적으로 위보다 큼) | **재임베딩 불필요**, 기존 색인 그대로 |

**결론: 임베딩은 교체하지 않는다.** +1.1 MTEB 를 위해 전체 재임베딩을 하고 hybrid 검색을
잃는 것은 타산이 맞지 않는다. 리랭커는 색인을 건드리지 않고 추가되며, 효과가 나지 않으면
**끄기만 하면 원복된다**(되돌리기 비용이 거의 0).

### 3-3. 모델 후보

| 모델 | 크기 | 라이선스 | 비고 |
|---|---|---|---|
| **`bge-reranker-v2-m3`** | 568M | Apache 2.0 | 현재 `bge-m3` 와 **같은 계열** — 다국어 토크나이저 거동이 일관됨. 다국어 기본값으로 가장 널리 배포됨 |
| `qwen3-reranker:0.6b` | 0.6B | Apache 2.0 | 100+ 언어, 32K ctx, instruction-aware |
| `qwen3-reranker:4b` / `:8b` | 4B / 8B | Apache 2.0 | 품질 최상이나 이 하드웨어에 과함 |

**권장: `bge-reranker-v2-m3`.** 이유는 품질 서열이 아니라 **일관성** — 1단계 임베딩과 같은
계열이라 한국어 토큰화 거동이 어긋나지 않고, 568M 이라 CPU 로도 실용 속도가 나온다.

### 3-4. 🔴 Bifrost 경유 이슈 — 이 기능의 핵심 쟁점

**문제의 연쇄:**

1. **Ollama 에 rerank 엔드포인트가 없다.** 2024-03 에 열린 요청 이슈(#3368)가 381 reaction 을
   모았으나 **머지된 PR 이 없고, 2026-10 현재 공식 API 문서에 reranking 항목 자체가 없다.**
2. 따라서 리랭커를 Ollama 로 서빙하는 정상 경로가 존재하지 않는다.
3. **Bifrost 는 OpenAI 호환 스펙을 미러링하는 LLM 게이트웨이**다
   (`/v1/chat/completions` · `/v1/embeddings`). 그런데 **rerank 는 OpenAI 표준 스펙에 없다** —
   Cohere · Jina 가 각자 `/v1/rerank` 를 내놨을 뿐 공통 규격이 아니다.
   즉 Ollama 가 지원한다 해도 Bifrost 쪽 패스스루가 별도로 필요하다.
4. 그런데 이 프로젝트는 **"모든 호출은 Bifrost 경유"를 명시적 원칙으로 둔다** —
   `src/embedding_function.py` 주석: *"Ollama 를 직접 부르면 접점이 하나 더 늘고
   관측·인증이 갈라지기 때문이다."*

**즉 리랭커는 이 프로젝트의 게이트웨이 원칙과 정면으로 충돌하는 첫 기능이다.**

#### 선택지 비교

**선택지 A — 인프로세스 cross-encoder (`sentence-transformers` / `FlagEmbedding`)**

* 방식: `fastapi_wiki_server.py` 프로세스 안에 모델을 직접 적재. HTTP 홉이 아예 없다.
* 장점
  * 가장 단순 — 새 컨테이너·포트·어댑터가 없다.
  * **CPU 구동 가능**(568M). 이 기기의 VRAM 예산(약 6.7GB)이 이미 빡빡하므로
    **CPU 로 도는 것이 단점이 아니라 장점**이다 — GPU 경합이 0 이다.
  * 되돌리기가 쉽다(플래그로 끄면 끝).
* 단점
  * **Bifrost 를 완전히 우회한다** → Langfuse 트레이스·통합 인증에서 빠진다.
  * 툴 서버에 `torch` · `transformers` 의존성이 추가된다(설치 용량 큼).

**선택지 B — 사이드카 어댑터(`/v1/rerank` 노출) + Bifrost 등록**

* 방식: 커뮤니티 어댑터(예: `dify-ollama-rerank-adapter`, `ollama-utils` 의
  reranking-endpoint 플러그인)를 띄워 표준 rerank API 로 감싼다.
* 장점: 게이트웨이 단일 창구 형태를 유지하는 **외형**은 지켜진다.
* 단점 — **가장 나쁜 조합이 될 위험이 크다.** Bifrost 가 rerank 라우트를 지원하지 않으면
  어댑터를 직접 호출하게 되는데, 그러면 **움직이는 부품만 하나 늘고 게이트웨이 이득은 0** 이다.
  * **2026-10-15 확인 결과 전제가 깨졌다.** Ollama 0.40 에도 rerank 엔드포인트가 없다
    (2024-03 이슈 #3368 미해결, 공식 API 문서에 `/api/embed` 만 존재). 게다가 rerank 는
    OpenAI 표준 스펙이 아니라 Bifrost 가 미러링할 대상 자체가 없다.
    → **선택지 B 는 기각한다.**

**선택지 C — chat 엔드포인트로 점수화 (Bifrost 경유 유지)**

* 방식: Qwen3-Reranker 는 실제로는 causal LM 이라 yes/no 로짓을 뱉는다 —
  `/v1/chat/completions` 로 프롬프트를 넣고 응답을 읽어 점수화한다.
* 장점: **원칙을 지킨다** — Bifrost 경유라 관측·인증이 유지되고 새 의존성이 없다.
* 단점
  * 제대로 된 점수에는 **logprobs 가 필요**한데 Bifrost·Ollama 경유 logprobs 지원이 불확실하다.
    없으면 거친 yes/no 만 얻어 **순위의 해상도를 잃는다**(리랭커의 존재 이유가 약해진다).
  * top-20 이면 **chat 호출 20회** → 지연이 크다.
  * 리랭커 모델을 Bifrost allow list 에 **태그까지 정확히** 등록해야 한다
    ([`modelfiles/README.md`](../modelfiles/README.md) 2장 — 누락 시 조용히 `403`).

#### ✅ 결정 — 선택지 A 확정 (2026-10-15)

**선택지 A(인프로세스 cross-encoder)로 진행한다. 원칙 예외를 아래와 같이 기록한다.**

근거:

1. **B 기각** — 전제가 실측으로 깨졌다(Ollama 0.40 에 rerank 없음, rerank 는 OpenAI 스펙 밖).
   게이트웨이 이득 없이 부품만 늘어난다.
2. **C 보류** — 원칙은 지키지만 logprobs 불확실성 때문에 **기능이 반쪽이 될 수 있고**,
   top-20 에 chat 호출 20회라 지연이 A 보다 훨씬 크다.
3. **A 의 유일한 실질 손실은 관측 공백**이며, 이것은 ⑤ 로 메운다 — 리랭커 지연·히트율을
   Prometheus 메트릭으로 직접 내보내면 **관측이 사라지는 게 아니라 Langfuse 에서 PLG 로
   이동하는 것**이다.

##### 원칙 예외 기록 (근거 보존용)

> **예외 대상:** 리랭커 1종(`bge-reranker-v2-m3`)의 추론 호출.
> **예외 내용:** 이 호출만 Bifrost 를 경유하지 않고 `fastapi_wiki_server.py` 프로세스 내에서 직접 실행한다.
> **불가피한 이유:** Ollama 에 rerank 엔드포인트가 없고(#3368 미해결), rerank 는 OpenAI 표준
> 스펙이 아니라 Bifrost 가 프록시할 라우트 자체가 존재하지 않는다. 즉 **게이트웨이 경유가
> 기술적으로 불가능**하며, 선택의 결과가 아니다.
> **보상 조치:** 관측을 포기하지 않는다 — `reranker_latency_seconds` ·
> `reranker_calls_total` 을 PLG 로 내보낸다(⑤).
> **한계:** 통합 인증(Bifrost 가상 키)에서는 빠진다. 단 이 호출은 **외부로 나가지 않고
> 프로세스 내부에 머물므로** 인증 경계를 넘지 않는다.

이 기록의 수준은 `src/embedding_function.py` 가 Bifrost 경유의 등가성을 실측으로 증명해
남긴 주석과 같은 급을 목표로 한다 — **"왜 어쩔 수 없었는지"가 코드 옆에 남아야 한다.**

#### 🔴 300ms 는 근거 없는 추정이었다 — 실측 스케일

| max_length | top-5 | top-20 | 쌍당 |
|---|---|---|---|
| 512 (기본) | 4,550ms | **18,932ms** | 947ms |
| 256 | 2,236ms | 9,406ms | 470ms |
| 128 | 1,222ms | 4,917ms | 246ms |

지연은 **쌍 수와 max_length 에 각각 선형**이다. 그리고 **max_length 를 줄이는 것은
해결책이 아니다** — 청크가 평균 845자(약 450토큰)라 128 로 자르면 청크의 70% 를
버린다. cross-encoder 를 쓰는 이유가 질의와 문서 토큰의 교차 어텐션인데, 문서를
잘라내면 **지연을 줄이는 만큼 리랭킹의 존재 이유가 깎인다.**
최선값(top-5 · max_length 128)도 1,222ms 로 목표의 4배다.

검토했으나 기각한 대안:

* **더 작은 모델**(`bge-reranker-base` 278M) — 약 2배 빨라도 자릿수가 그대로이고,
  v2-m3 를 고른 이유였던 한국어 품질을 잃는다
* **ONNX int8** — 보통 2~3배이므로 역시 자릿수가 바뀌지 않는다
* **GPU** — `torch` 가 CPU 전용이고(AMD RX 6600 XT 는 Windows ROCm 미지원),
  onnxruntime-directml 로 우회해도 **Ollama 와 VRAM 을 다툰다** — A 안을 고른
  이유가 바로 "GPU 경합 0" 이었으므로 자기모순이다

#### ✅ 확정 조치 — 기본값을 끄고 비대화형 경로로 한정한다

* `WIKI_RERANK` **기본값 `0`(꺼짐)**. 켜려면 명시적으로 `1`
* **대화형 경로(HTTP 툴 서버 · ReAct 에이전트)에는 켜지 않는다** — 질의당 19초는
  에이전트 루프에서 쓸 수 없다
* **지우지는 않는다** — 10건 중 5건에서 순서가 바뀌었으므로 품질 신호는 실재한다.
  지연이 무관한 경로에 값이 있다: **④ 야간 배치**, 오프라인 평가·비교
* 되돌리기 비용은 그대로 0 이다(플래그로 끄면 벡터 검색 순서로 복귀)

> **교훈 기록:** 설계 단계에서 적은 "300ms 이내"는 측정이 아니라 추정이었다.
> 이번에 64배 틀렸다. **성능 기준은 대상 하드웨어에서 재본 뒤에 적는다** —
> 특히 파라미터 수와 입력 길이가 곧 지연인 cross-encoder 류에서는.

## ④ 야간 배치 — 임베딩 내리고 최대 컨텍스트 모델 투입

### 착안점
현재 `num_ctx` 상한(16,384 / 65,536)은 **모델 한계가 아니라 임베딩 동시 상주 때문**이다.
그런데 `src/agent/wiki_agent.py:125` 에 **이미 `unload_ollama_model()` 이 있다.**
야간에는 임베딩을 내리고 예산 전체(약 6.7GB)를 한 모델에 쓸 수 있다.

[`context_limit_experiment.md`](context_limit_experiment.md) 실측값으로 본 야간 전용 후보:

| 후보 파생 모델 | num_ctx | 적재 크기 | 야간 가능? |
|---|---|---|---|
| `qwen3.5-32k` | 32,768 | 6.62GB | ✅ 가능하나 여유 없음 |
| ✅ **`gemma4-e4b-128k`** (채택) | 131,072 (네이티브 최대) | **3.38GB · 100% GPU** | ✅ **확정** |

### ✅ 야간 전용 모델 확정 — `gemma4-e4b-128k` (2026-10-15 실측)

`modelfiles/gemma4-e4b-128k.Modelfile` 생성 후 실측한 결과다.

```
gemma4-e4b-128k:latest   size=3.38GB  vram=3.38GB  gpu=100.0%  ctx=131072
```

추정값 3.4GB 와 사실상 일치했다. `qwen3.5-32k`(6.62GB)보다 **절반 이하 크기로 컨텍스트는 4배**라
선택의 여지가 없었다.

#### 🔴 실측 중 발견 — 이 모델을 적재하면 임베딩이 축출된다

적재 전 `bge-m3`(0.66GB)가 올라가 있었는데, `gemma4-e4b-128k` 를 적재한 직후
**`/api/ps` 에서 `bge-m3` 가 사라졌다.** 두 모델 합계는 4.04GB 로 VRAM 예산(약 6.7GB)에
충분히 들어가는데도 축출됐다.

추정 원인: Ollama 가 적재 **전에 계산하는 메모리 예상치**가 131,072 컨텍스트에 대해
실제 상주 크기(3.38GB)보다 훨씬 크게 잡혀, 자리를 만들려고 기존 모델을 내린 것으로 보인다.
(`OLLAMA_MAX_LOADED_MODELS=2` 라 개수 상한 때문은 아니다.)

**이 발견이 ④ 설계에 주는 함의 — 세 가지:**

1. `[2] 임베딩 언로드` → `[3] 야간 모델 적재` **순서는 정돈이 아니라 필수다.**
   순서를 지키지 않아도 Ollama 가 알아서 축출하지만, 그러면 **우리가 모르는 시점에
   임베딩이 내려간다** — 복구 책임 지점이 사라진다.
2. 🔴 **야간 시간대가 아닐 때 이 모델을 호출하면 RAG 가 조용히 깨진다.**
   `[6]` 의 복구 단계가 없는 경로(사람이 Open WebUI 에서 호다닥 불러보는 등)로 적재되면
   임베딩이 내려간 채 남는다. → **Bifrost allow list 에 넣지 않는다**(아래 참고).
3. `[6]` 의 "재적재 **확인**까지가 복구" 정의가 옳았다는 실증이다 — 언로드만 하고
   확인하지 않으면 이 상태를 놓친다.

> **운영 규칙 확정:** `gemma4-e4b-128k:latest` 는 **Bifrost 에 등록하지 않는다.**
> Open WebUI 모델 목록에 노출되지 않게 해서 사람이 실수로 부르는 경로를 막는다.
> 야간 배치 스크립트만 Ollama 를 직접 호출해 쓴다(배치는 복구 책임을 지는 유일한 경로다).

### ✅ 확정 설계 (2026-10-15) — 위험 완화를 파이프라인에 내장

아래는 "제안"이 아니라 **구현해야 할 확정 설계다.** 위험 항목을 별도 주의사항으로 두지 않고
**파이프라인 단계로 끌어올렸다** — 주의사항은 지켜지지 않지만 단계는 실행되기 때문이다.

```
02:00  배치 시작
   │
   ├─ [0] 사전 점검 (gate) ─── 하나라도 실패하면 즉시 중단하고 아무것도 건드리지 않는다
   │        ├─ 선행 배치가 살아있나? (PID 락 파일) → 있으면 종료
   │        ├─ wiki_agent 가 처리 중인 파일이 있나? → 있으면 종료 (경합 회피)
   │        └─ 현재 적재 상태 기록 (/api/ps) → 복구 기준점으로 저장
   │
   ├─ [1] 배치 모드 진입 선언
   │        └─ 락 파일 생성 + batch_mode 메트릭 1 로 올림 (⑤ 연계)
   │
   ├─ [2] bge-m3 언로드 (keep_alive=0)  ← 약 0.66GB 확보
   │
   ├─ [3] 야간 전용 고ctx 모델 적재
   │        └─ 적재 직후 100% GPU 인지 검증 → CPU 분할이면 즉시 [6] 으로 점프
   │
   ├─ [4] vault 전체 크로스체크
   │        ├─ 연결 안 된 관련 문서 쌍 제안
   │        ├─ 중복·충돌 서술 탐지
   │        └─ 태그 누락 보완 제안
   │
   ├─ [5] 결과를 제안 파일로 기록 (문서를 직접 고치지 않는다)
   │
   └─ [6] finally ─── 예외·강제종료·CPU분할 어느 경로로 왔든 반드시 실행
            ├─ 야간 모델 언로드
            ├─ bge-m3 재적재 + **적재 성공을 확인** (확인까지가 복구다)
            ├─ 확인 실패 시 → 재시도 3회 → 그래도 실패면 Discord 즉시 알림
            ├─ batch_mode 메트릭 0 으로 내림
            └─ 락 파일 삭제
```

#### 확정된 위험 완화 항목

| 위험 | 완화책 (설계에 반영됨) |
|---|---|
| 🔴 배치 중단 시 임베딩이 내려간 채 남아 **RAG 전면 장애** | `[6]` 을 `finally` 로 고정 + **재적재 확인까지** 복구로 정의 + 3회 재시도 + 실패 시 Discord 알림. `[0]` 에서 복구 기준점을 미리 저장 |
| `wiki_agent` 와 모델 적재 경합 | `[0]` 게이트에서 처리 중 파일 확인 후 중단. 배치는 **`wiki_agent` 를 멈추지 않는다** — 멈추면 그 사이 입력이 유실된다 |
| `OLLAMA_MAX_LOADED_MODELS=2` 상한 충돌 | `[2]` → `[3]` 순서를 고정(**반드시 내린 뒤 올린다**). 동시 적재를 시도하지 않으므로 상한에 걸리지 않는다 |
| 고ctx 모델이 CPU 분할로 적재 | `[3]` 에서 즉시 검증해 분할이면 **작업을 수행하지 않고** `[6]` 으로 간다 — 느린 채 밤새 도는 것을 막는다 |
| 배치 중복 실행 | `[1]` PID 락 파일. `[0]` 에서 선행 배치 확인 |
| 아침에 깨진 상태를 모름 | `batch_mode` 메트릭 + `ollama_model_loaded` 로 Grafana 알림(⑤) |

* **비용 0** — 클라우드 호출이 없고 전기만 쓴다.
* `#personal` 데이터를 다뤄도 **로컬 전용이라 프라이버시 경계를 지킨다** — 이 기능은
  ⑥(Jev) 을 쓰지 않는다. vault 전문을 외부로 보내지 않는 것이 이 설계의 전제다.

### 완료 기준
* 배치 1회 완주 후 **제안 파일이 생성**되고, 그중 사람이 채택할 만한 항목이 1건 이상 있다.
* 배치 종료 후 `GET /api/ps` 에 **`bge-m3` 가 복구**되어 있다.
* 고ctx 모델이 **100% GPU 로 적재**된다(CPU 분할이면 야간이라도 실용성이 없다).
* 🔴 **고장 주입 시험:** `[4]` 진행 중 프로세스를 강제 종료(`Stop-Process -Force`)했을 때
  **`bge-m3` 가 복구되는지 직접 확인한다.** `finally` 를 작성한 것만으로 복구된다고 보지 않는다
  — 강제 종료는 `finally` 를 건너뛰므로, 이 시험에서 복구가 안 되면 **워치독
  (`scripts/exporter_watchdog.ps1` 패턴)으로 보강해야 한다.**

### 구현 시 주의
* 작업 스케줄러 등록은 **관리자 권한이 필요**하다 — `scripts/manage_tasks.ps1` 패턴을 쓰되,
  등록 실행은 사람이 상승된 셸에서 해야 한다(이 세션에서는 대행 불가).
* `[0]` 의 "처리 중 파일" 판정 기준은 `wiki_agent` 의 Watchdog 상태와 맞춰야 한다 —
  RAW_DIR 에 새 파일이 있는지로 단순 판정하면 오탐이 난다.

## ⑤ PLG 에 로컬 모델 메트릭 연결 — 계측 먼저

### 현재 상태
[`plg_monitoring_design.md`](plg_monitoring_design.md) 구축 4번(개발 PC exporter +
`ollama_model_gpu_ratio`)이 **이미 대기 중**이다. 이 제안은 그 범위를 로컬 모델 품질·성능까지
넓히는 것이다 — 추가 비용이 가장 작은 기능이다.

### 제안 메트릭

| 메트릭 | 상태 | 출처 | 왜 필요한가 |
|---|---|---|---|
| `ollama_model_gpu_ratio` | ✅ **기존** | `/api/ps` | CPU 분할 즉시 감지. 구축 4번의 완료 기준 지표 |
| `ollama_model_loaded{model}` | ✅ **기존** | `/api/ps` | 적재된 모델 목록 |

| `ollama_model_reload_total{model}` | 🔨 **추가 완료** | `/api/ps` 전이 감지 | 채팅↔임베딩 전환 시 약 7초 재적재 비용의 발생 빈도 |
| `nightly_batch_mode` | 🔨 **추가 완료** | 락 파일 | ④ 의 배치 구간 판별 |
| `nightly_batch_lock_age_seconds` | 🔨 **추가 완료** | 락 파일 mtime | 락이 남은 채 나이가 늘면 배치가 복구 단계를 못 거치고 죽은 것 |
| `llm_tokens_per_second` | ❌ **구현 안 함** | Bifrost `/metrics` | PromQL 로 유도된다 — 아래 참고 |
| `llm_ttft_seconds` | 🔴 **미해결 (재개)** | 없음 | **Bifrost 에 TTFT 메트릭이 없다** — 2026-10-17 실측으로 확인. 아래 참고 |
| `reranker_*` | ⏭️ ③ 구현 시 | ③ 인프로세스 계측 | ③ 이 Bifrost 를 우회해 생기는 관측 공백을 메운다 |
| `jev_*` | ⏭️ ⑥ 구현 시 | ⑥ SDK 호출 계측 | ⑥ 이 Bifrost 를 우회해 생기는 관측 공백을 메운다 |

#### 🔴 `ollama_model_resident` 를 따로 만든 이유

`/api/ps` 는 **적재된 모델만** 돌려준다. 그래서 `ollama_model_loaded{model="bge-m3:latest"}` 는
모델이 내려간 순간 **시계열 자체가 사라진다.** 그 상태로 알림을 걸면 PromQL 필터식이 빈 결과를
내고 Grafana 가 이를 NoData 로 취급해 오탐이 된다 —
[`troubleshooting.md`](troubleshooting.md) 섹션 18 증상 4 에 기록된 바로 그 함정이다.

`ollama_model_resident` 는 `WATCHED_MODELS` 목록에 대해 **미적재일 때도 0 을 낸다.**
이것이 ④ 의 장애 알림을 성립시키는 전제다:

```promql
# "배치가 아닌데 임베딩이 내려가 있다" = RAG 전면 장애
ollama_model_resident{model="bge-m3:latest"} == bool 0
  and on() nightly_batch_mode == bool 0
  and on() ollama_up == bool 1
```

`ollama_up == bool 1` 을 함께 묶는 이유: Ollama 자체가 죽었으면 `collect_ollama_metrics` 가
조기 반환해 `resident` 를 내지 않으므로, 그 경우는 **별도 알림(`ollama_up`)이 담당**해야 한다.

#### 🔴 TTFT 보류 — 재개한다 (2026-10-17 실측으로 이전 결론 정정)

**정정:** 직전 조사에서 *"Bifrost 가 `bifrost_stream_first_token_latency_seconds` 로
TTFT 를 이미 낸다"* 고 적고 구현 불필요로 결론냈다. **이 결론은 틀렸다.**
실제 엔드포인트를 인증 통과해 조회한 결과 **그 메트릭은 존재하지 않는다.**
`bifrost_cost_total`(클라우드 지출)도 없다. 두 이름은 제작사 블로그에만 있는 것이었고,
"블로그 기준이니 라이브 확인이 필요하다"고 달아둔 경고가 실제로 적중했다.

**실제로 존재하는 Bifrost 메트릭 (2026-10-17 실측 전수):**

| 메트릭 | 쓸 데 |
|---|---|
| `bifrost_upstream_latency_seconds` | 요청 **전체** 지연 (TTFT 아님) |
| `bifrost_input_tokens_total` · `bifrost_output_tokens_total` | 토큰량 |
| `bifrost_upstream_requests_total` · `bifrost_success_requests_total` | 성공률 |
| `bifrost_request_retries` · `bifrost_provider_key_up` | **폴백 체인 모니터링** — 로드맵 OTel ④ 가 원했던 것 |
| `bifrost_active_requests` | 동시 처리 중 요청 수 |
| `http_request_duration_seconds` · `go_*` · `process_*` | HTTP/런타임 표준 |

따라서:

* ✅ **`tokens_per_second` 는 구현하지 않는다** — 유도된다:
  `rate(bifrost_output_tokens_total[5m]) / rate(bifrost_upstream_latency_seconds_sum[5m])`
* 🔴 **TTFT 는 대체물이 없다.** `bifrost_upstream_latency_seconds` 는 생성 시간까지 포함한
  **전체** 지연이라 TTFT 의 대리 지표로 약하다 — 특히 thinking 모델은 생성 시간이 전체를
  지배해서 TTFT 개선이 희석돼 보이지 않는다.

**남은 선택지 (미결, 다음 작업으로 미룸):**

1. **`scripts/benchmark_bifrost.py` 에 TTFT 측정을 추가한다** — 현재 `latency_sec` ·
   `tokens_per_sec` 만 재고 **스트리밍을 쓰지 않는다.** 스트리밍으로 바꿔 첫 청크
   도착 시각을 재면 된다. 런타임 업그레이드 전후 비교는 상시 메트릭이 아니라
   **일회성 측정**이 맞는 일이므로 이쪽이 목적에 부합한다. (권장)
2. 상시 메트릭이 꼭 필요하면 앱 측 계측을 직접 넣는다 — 비용이 크고 효용은 1번보다 낮다.
3. TTFT 를 포기하고 전체 지연만 본다.

> **교훈 기록:** 벤더 블로그의 메트릭 이름은 1차 근거가 아니다. 이번에 실제로 두 개가
> 없었다. 메트릭에 의존하는 결론은 **엔드포인트 조회로만 확정**한다.
##### 🔴 그러나 Bifrost 메트릭에는 구조적 사각지대가 있다

Bifrost 메트릭은 **Bifrost를 지나는 호출만** 본다. 그런데 이 계획은 게이트웨이 예외를
세 군데 만든다 — 각 예외가 곧 계측 사각지대이며, **그래서 보상 메트릭이 선택이 아니라 필수다.**

| 예외 | Bifrost 메트릭에 안 잡히는 것 | 보상 |
|---|---|---|
| ③ 리랭커 (인프로세스) | 리랭킹 지연·호출수 | `reranker_*` (⑤) |
| ④ 야간 배치 (Ollama 직접 호출) | 배치의 토큰·지연 전부 | `nightly_batch_*` + 배치 자체 계측 |
| ⑥ Jev (SDK 직접) | 판정 호출 전부 | `jev_*` (⑤) |

> 즉 **"모든 호출은 Bifrost 경유" 원칙이 곧 관측의 완전성이었다.** 예외를 둘 때마다
> 그만큼을 따로 메워야 한다 — 이것이 원칙을 깨는 실제 비용이다.

### 완료 기준
* `ollama_model_gpu_ratio` 가 Grafana 에서 값을 낸다(구축 4번의 기존 완료 기준과 동일).
* `llm_ttft_seconds` 로 **런타임 업그레이드 전후를 수치로 비교**할 수 있다.
* ④ 의 임베딩 미복구 상태에 대해 **알림이 실제로 울리는 것까지 확인**한다 —
  규칙을 만든 것만으로 작동한다고 말하지 않는다.

### 주의
* 알림 규칙은 `bool` 비교로 짠다 — PromQL 필터식은 조건 미충족 시 빈 결과를 내고 Grafana 가
  이를 NoData 로 취급해 오탐을 낸다([`troubleshooting.md`](troubleshooting.md) 섹션 18 증상 4).
* exporter 는 루프백 전용 바인딩을 유지한다(`127.0.0.1:13092`) — 노출면을 늘리지 않는다.
* ⑥ 을 도입하면 `jev_*` 메트릭(호출수·지연·확률 분포·기각률)도 같은 exporter 에 추가한다.

## ⑥ Jev (TypeSafe AI) 결정 모델 — 검토 결과

### 6-1. Jev 는 무엇인가

2026-09-15 TypeSafe AI 가 공개한 **"System One" 결정 모델**이다. LLM 이 아니다.

| 항목 | 내용 |
|---|---|
| 입출력 | **state**(텍스트/JSON) + **코드로 정의한 타입 질문** → 구조화된 값만 반환. 산문·근거·코드를 내지 않는다 |
| 질문 유형 | `Choice`(택일) · `Score`(루브릭 점수) · `Noul`(명제가 참일 확률 0~1) |
| 아키텍처 | **비자기회귀(non-autoregressive)** — 토큰을 하나씩 생성하지 않고 단일 패스로 결정. 한 요청 내 질문들이 **병렬 처리**된다 |
| 지연 | 종단 70~500ms |
| 가격 | 입력 100만 토큰당 **$0.042**, 출력 토큰 무과금 |
| 컨텍스트 | 64,000 (state + 질문), 최장 질문 32,000 |
| 학습 | RLCD(Reinforcement Learning for Calibrated Decisions) — **확률이 캘리브레이션되어 있다** |
| 배포 | 🔴 **클라우드 전용.** 로컬 구동 불가 |
| 호환성 | 🔴 **OpenAI 호환 아님.** 독자 요청/응답 형식 |

**중요한 한계:** 텍스트 생성 불가 · 다단계 추론·산술·날짜 비교에 취약 ·
적대적 입력에 답이 흔들릴 수 있음 · "환각하지 않는다"는 **스키마를 위반하지 않는다는 뜻일 뿐**
(유효하지만 틀린 답은 나온다).

### 6-2. 리랭커로서의 Jev — 벤치마크가 있다

추측이 아니라 **BEIR 로 측정된 수치가 있다**(BM25 top-30 재정렬, SciFact·NFCorpus·FiQA 평균):

| 리랭커 | nDCG@10 | 비고 |
|---|---|---|
| `mxbai-rerank-v3.1-listwise` | **0.511** | 최상위 |
| Voyage `rerank-3` | 0.504 | |
| **Jev** (무튜닝) | **0.501** | 1,000 질의당 $0.54 |
| Cohere `rerank-v3.5` | 0.486 | |

즉 **전용 상업 리랭커와 대등하다.** 기성 라이브러리도 있다 —
[`hotchpotch/jev-reranker`](https://github.com/hotchpotch/jev-reranker) 의
`relevance_rerank()` 가 점수화·정렬·임계값 필터링을 한 번에 한다.
TypeSafe 자체 사례로는 법률 검색 top-10 이 38% → 62% (1,200 호출 $0.0645),
검색 리랭킹 top-1 이 5% → 18% 로 보고돼 있다.

> ⚠️ **`bge-reranker-v2-m3` 와의 직접 비교 수치는 찾지 못했다.** 위 표에 bge 계열이 없어
> "Jev 가 A 안보다 낫다/못하다"를 수치로 말할 수 없다 — **이것이 미결 사항이다.**

### 6-3. 🔴 그런데도 ③ 의 1차 경로로는 쓰지 않는다

| 쟁점 | A 안 (`bge-reranker-v2-m3`, 확정) | Jev |
|---|---|---|
| 데이터 이동 | **프로세스 내부에 머문다** | **외부 API 로 나간다** |
| `#personal`·이력서·회고 | ✅ 사용 가능 | ❌ **정책상 불가** ([`implementation_plan.md`](implementation_plan.md) 4-2: 로컬 전용) |
| Bifrost 경유 | 불가 (rerank 라우트 없음) | **불가 (OpenAI 호환 아님)** — 같은 문제를 네트워크까지 얹어서 겪는다 |
| 비용 | 0 | 질의당 과금 |
| 가용성 | 네트워크 무관 | 외부 장애·레이트리밋에 종속 |
| VRAM | 0 (CPU) | 0 |

**결론: 위키 RAG 의 기본 리랭커는 A 안으로 간다.** 이유는 품질 서열이 아니라
**프라이버시 경계**다 — 위키에는 `#personal` 이 섞여 있고, 질의 시점에 그것을 분리하는
신뢰할 수 있는 수단이 없다. 경계가 모호한 곳에 외부 API 를 놓지 않는다.

또한 Jev 를 1차로 쓰면 **A 안이 피하려 한 문제(게이트웨이 우회)를 그대로 겪으면서
네트워크 의존과 과금까지 추가**된다 — 교환 조건이 맞지 않는다.

### 6-4. ✅ Jev 가 실제로 맞는 자리 — 연결 권장 지점

Jev 의 성격은 **"소프트웨어 안에서 빠르고 싼 타입 판정"**이다. 이 프로젝트에서 그 모양인 일:

| 우선 | 연결 지점 | 왜 Jev 인가 | 프라이버시 |
|---|---|---|---|
| **1** | **CI 적대적 검증자** ([`implementation_plan.md`](implementation_plan.md) 4-3) | *"이 발견을 반박하라. 불확실하면 기각하라"* 는 **캘리브레이션된 확률에 임계값을 거는 일**이다 — Jev 의 `Noul` 이 정확히 이것. 현재 Haiku/Gemini Flash 로 계획돼 있는데 비용이 수백 분의 1 | ✅ 자기 저장소 diff |
| **2** | **스크래핑 원문 프롬프트 인젝션 차단** | `discord_bot.py` 가 `r.jina.ai` 로 **임의 웹페이지를 긁어 파이프라인에 넣는다** — 실재하는 인젝션 경로다. Jev 는 인젝션 탐지를 0.99 확률로 보고 | ✅ 공개 웹 |
| **3** | **①의 도구 호출 안전 판정** | 로컬 모델이 자율로 도구를 부르기 시작하면 사전 판정이 필요해진다 (사례: 약 250ms/건) | ✅ 내부 |
| 4 | `#tech` 전용 2차 리랭킹 | 공개 기술 문서에 한해 A 안 뒤에 얹는 실험 | ⚠️ 태그 분리 확실할 때만 |
| ❌ | wiki_agent `classify` 노드 | 모양은 가장 잘 맞지만, **분류 시점에는 그 문서가 `#personal` 인지 아직 모른다** — 판정하려고 보내는 순간 경계를 넘는다 | ❌ **불가** |

> **1번이 가장 가치가 크다.** 적대적 검증 설계는 "파인더 10여 개 → 검증자가 반박 → 생존한
> 것만 게시"인데, 검증자가 **확률을 주지 못해 임계값을 걸 수 없다**는 것이 원래 설계의 약점이었다.
> Jev 는 그 약점을 직접 메운다 — `Noul` 확률에 컷을 거는 것이 곧 "불확실하면 기각"이다.

### 6-5. 연결 방법

접근 경로 3가지:

1. **OpenRouter** — `jev-latest` · `jev-1.13` 제공. **이 프로젝트에 가장 적합**하다 —
   [`implementation_plan.md`](implementation_plan.md) 에 이미 OpenRouter 를 모델 실험 경로로
   두었고, Bifrost 에 OpenRouter 프로바이더로 묶으면 **과금·관측이 기존 체계에 들어온다.**
2. 직접 가입 — `console.typesafe.ai`. ⚠️ **2026-09-22 기준 신규 가입이 중단됐다**(재개 여부 미확인).
3. Vercel AI Gateway — `typesafe-ai/jev`. 이 프로젝트 스택과 무관.

### ✅ 6-6. 연결 방식 확정 (2026-10-15) — Bifrost 경유 불가

**결론: Bifrost 로는 Jev 를 쓸 수 없다. 공식 TypeSafe SDK 를 직접 호출한다.**

조사 결과 OpenRouter 에는 **이름이 비슷한 서로 다른 두 제품**이 있고, 이것이 혼동의 원인이었다.

| OpenRouter 모델 ID | 정체 | 엔드포인트 | ⑥ 에 쓸 수 있나 |
|---|---|---|---|
| `typesafe/jev-router` | **모델 라우터.** Jev 로 과제 난이도를 판정해 **다른 모델**을 고르고, 선택된 그 모델이 응답을 생성한다 | `/api/v1/chat/completions` (OpenAI 호환) | ❌ **아니다.** 라우팅된 채팅 답변이 나올 뿐, **타입 판정·확률이 나오지 않는다** |
| `typesafe/jev-1.13` · `jev-latest` | **결정 모델 본체** | 채팅 엔드포인트가 **HTTP 400 으로 거부**. 별도 Decisions / System One 계열 경로 | ✅ 이게 필요한 것이지만 **OpenAI 형식이 아니다** |

따라서 Bifrost 경유가 불가능한 이유는 ③ 리랭커와 **구조적으로 완전히 동일하다**:

* Bifrost 는 OpenAI 스펙 라우트(`/v1/chat/completions` · `/v1/embeddings`)를 미러링한다.
* Jev 의 타입 결정 호출은 그 스펙 밖이다 — **프록시할 라우트 자체가 없다.**
* OpenAI 호환인 `jev-router` 를 쓰면 Bifrost 를 통과시킬 수는 있으나,
  **얻는 것이 ⑥ 이 필요한 것(캘리브레이션된 확률)이 아니다.**

> ⚠️ **출처 신뢰도 — 확정의 근거와 한계를 구분해 적는다.**
> **확정의 근거**(신뢰 높음): OpenRouter 공식 `jev-router` 문서가 이것을 "모델·추론 강도를
> 고르는 라우터"로 설명하고 Chat Completions 를 지원한다고 명시하며, `typesafe/jev-1.13` 은
> 언급조차 하지 않는다. 또한 Jev 의 공식 API 형태 자체가 `state` + `Choice`/`Score`/`Noul`
> 질문이고 **"OpenAI 호환 아님"**이다(6-1). 이 두 가지로 "Bifrost 프록시 불가"는 확정된다.
> **한계**(신뢰 낮음): 결정 모델의 **정확한 엔드포인트 경로**는 3rd-party 출처뿐이고
> 공식 라우터 문서에는 없다(한 경로는 이름에 `alpha` 가 들어간다). **구현 직전에 TypeSafe
> 공식 문서로 경로를 다시 확인할 것** — 경로는 바뀔 수 있지만 위 구조적 결론은 바뀌지 않는다.

**확정 연결 방식:**

1. **공식 TypeSafe SDK(Python)를 직접 호출한다.** 계정은 확보 완료(2026-10-15).
2. ③ 과 같은 급으로 **원칙 예외를 기록한다** — 아래.
3. 관측은 `jev_*` 메트릭으로 PLG 에 낸다(⑤). Langfuse 트레이스에는 안 잡힌다.

##### 원칙 예외 기록 (Jev)

> **예외 대상:** Jev 결정 호출.
> **예외 내용:** Bifrost 를 경유하지 않고 TypeSafe SDK 로 직접 호출한다.
> **불가피한 이유:** Jev 의 타입 결정 API 는 OpenAI 스펙이 아니라 Bifrost 가 미러링할
> 라우트가 존재하지 않는다(③ 리랭커와 동일한 구조적 제약). OpenAI 호환인 `jev-router` 는
> 결정 모델이 아니라 모델 라우터이므로 대체가 되지 않는다.
> **③ 과 다른 중대한 차이:** 리랭커는 프로세스 내부에 머물지만 **Jev 는 외부로 데이터를 보낸다.**
> 따라서 인증 경계를 실제로 넘으며, **`#personal` 차단을 코드 경로로 보장해야 한다**(단순 주의 금지).
> **보상 조치:** `jev_calls_total` · `jev_latency_seconds` · `jev_probability_bucket` ·
> `jev_rejected_total` 을 PLG 로 내보낸다.

### 완료 기준
* 연결 지점 1(CI 검증자)에서 **기각률과 확률 분포가 기록**되고, 임계값을 바꿀 때
  PR 코멘트 건수가 실제로 변한다.
* 연결 지점 2에서 **알려진 인젝션 문구를 심은 테스트 페이지가 실제로 차단**된다 —
  규칙을 붙인 것만으로 막힌다고 보지 않는다.
* Jev 호출이 `#personal` 데이터를 **한 건도 포함하지 않음**을 코드 경로로 보장한다.

### 확정 착수 순서

```
⑤ 메트릭        ──→  ① 툴 콜링      ──→  ③ 리랭커(A안)  ──→  ② 이미지 편입
(계측 먼저)           (최우선 기능)        (①의 품질 보강)      (독립)
    │                     │                                    
    │                     └──→ ④ 야간 배치 (①의 오프라인 확장)
    │
    └──→ ⑥ Jev: CI 검증자 → 인젝션 차단 → (①착수 후) 도구 안전 판정
         ※ ⑥ 은 ①~④ 와 독립이라 병행 가능
```

**공통 원칙:** 모든 기능은 **완료 기준을 수치나 관측 가능한 상태로** 적었다. 만들어 둔 것과
작동하는 것은 다르다 —

* ③ 은 "top-5 가 실제로 바뀌는지"
* ④ 는 "**강제 종료해도 임베딩이 복구되는지**"
* ⑤ 는 "알림이 실제로 울리는지"
* ⑥ 은 "**심어둔 인젝션 문구가 실제로 차단되는지**"

를 확인하기 전까지 완료로 보지 않는다.

> **`deepseek-r1:14b` 유지 결정에 따른 운영 메모.**
> 8.99GB 로 VRAM 예산(약 6.7GB)을 넘어 **항상 CPU 분할**이며, thinking 은 현 라인업
> (`qwen3.5:9b` · `gemma4:e4b`)이 네이티브로 지원해 역할이 겹친다. 그래도 두는 이유는
> `🛠️ Refactoring Master` 페르소나의 베이스 모델이고, 심층 리팩토링에서 14B 체급의
> 지식 폭이 필요한 경우가 있기 때문이다.
> * 라우팅 우선순위는 **낮게** 둔다 — 기본 경로에 넣지 않고 사람이 명시적으로 고를 때만 쓴다.
> * `④` 야간 배치 모델로는 쓰지 않는다(CPU 분할 상태로 밤새 도는 것이 가장 나쁜 조합이다).
> * 다른 모델과 동시 선택(멀티모델 채팅)하면 재적재 경합이 심하다
>   ([`llm_webui_config.md`](llm_webui_config.md) 4장 경고 참고).
